# PROTOTYPE

> Status: Draft v0.1  
> 対象: 2026-08-16時点のPrototype（#35 / PR #36 まで反映）
> この文書は、`GAME_CONCEPT.md` / `GAME_DESIGN.md` で整理したゲーム全体の構想のうち、最初に実際に動かして検証する範囲を定義する。  
> 現時点では、ゲーム全体のMVPではなく **「探索ループ・プロトタイプ」** として扱う。

## 1. プロトタイプの目的

最初から100層、オンライン協力、レイド、職業、生産などを実装するのではなく、まず一人で遊べる最小構成を作る。

このプロトタイプで確認したい中心的な問いは、

> **「スタミナをいくつ使うか決めて探索に出し、ゲーム側で処理された結果を確認し、次の行動を決める」というサイクルに、ゲームとしての面白さがあるか。**

である。

ゲーム全体ではボス攻略やプレイヤー間の相談・編成が重要な体験になるが、このプロトタイプではそこまでを一度に検証しない。

まず、最小単位となる探索部分が成立するかを確認する。

**確定度：高**

この試作は、ゲーム全体の完成形を縮小したものではない。

検証対象を絞った **探索システムの試作** である。

## 4. プレイヤーが行うこと

1. ヘッダーで現在階層、現在地、踏破率、スタミナを確認し、左カラムでHPとEXPを確認する
2. 育成・戦術を決める
3. アルマセントからアルンの森、または解放済みのゴブリンの巣穴へ移動する
4. 探索に使用するスタミナ量を決める
5. 連続処理された探索イベントと戦闘結果を確認する
6. HPと探索深度を見て、続行か帰還か判断する
7. 街で宿屋、成長ポイント割り振り、素材換金を行う
8. 得たGoldを保持して再探索する

進行中クエストは左カラムのサブ情報として扱い、判断を止めずに必要なときへ確認する（`GAME_DESIGN.md`「25. UI・情報表示の優先順位」）。確認順は次の意味になる。

```text
現在地 / 踏破率 / HP / スタミナを確認
↓
行動を決める
↓
進行中クエストは必要に応じて確認
```

重要なのは、**探索前に決める → 結果を見る → 街で準備する → 次を決める**という流れである。

## 5. 探索イベント

### 5.1 現在の実装

探索開始後は、投入スタミナ10につき1回の**探索処理単位**を連続処理する。Issue #138で、1つの探索処理単位につき一次結果を1つだけ発生させる排他方式へ変更した（15.18参照）。

```text
探索処理1単位
↓
一次抽選（5カテゴリから1つだけ）
├ アイテムドロップ → ドロップ抽選ランク → ランク内素材抽選
├ モンスター遭遇   → 通常敵／強敵 → 対象モンスター抽選 → 戦闘
├ イベント発生     → 痕跡・回復地点等
├ 探索失敗         → 罠・進行なし
└ 探索進行         → 通常進行 / 近道 / 隠し通路
```

一次抽選率はロケーション別に持つ。

| 一次結果 | アルンの森 | ゴブリンの巣穴 |
|---|---:|---:|
| アイテムドロップ | 10% | 5% |
| モンスター遭遇 | 20% | 35% |
| イベント発生 | 5% | 10% |
| 探索失敗 | 5% | 10% |
| 探索進行 | 60% | 40% |

二次抽選は、Issue #78で置いた既存イベントの重みをそのまま**相対weight**として引き継ぐ。一次確率へ再加算しない。

| 一次カテゴリ | アルンの森の候補（相対weight） | ゴブリンの巣穴の候補（相対weight） |
|---|---|---|
| 探索進行 | 通常進行 17 (+4) / 近道発見 8 (+8) / 隠し通路 4 (+12) | 通常進行 18 (+4) / 近道発見 9 (+8) / 隠し通路 5 (+12) |
| モンスター遭遇 | 通常敵 33 / 強敵 4 | 通常敵 35 / 強敵 5 |
| イベント発生 | 人の利用痕跡 5 / ゴブリンの痕跡 5 / 回復地点 3 | 拠点痕跡 5 / 回復地点 3 |
| 探索失敗 | トラップ 4 / 進行なし 5 | 粗雑な罠 5 / 進行なし 3 |

**探索進行だけが個人探索深度と世界共有踏破率を進める。** モンスター遭遇で戦闘に勝利しても、その探索処理単位では進行を加算しない。痕跡系イベントが持っていた `+4` の進行も加算しない。

トラップ・粗雑な罠はHPを10減少させ、HPは0未満にならない。回復地点はHPを20回復し、最大HPを超えない。どちらも探索進行・探索ドロップは同時発生させない。

アイテムドロップは、ドロップ抽選ランク（Rare 1% / Uncommon 20% / Common 79%）を引いてから、ロケーション別・ランク別の素材テーブルから1個取得する。テーブルの内容は15.18に記載する。

ゴブリンの痕跡イベントは巣穴の解放条件ではない。巣穴は従来どおりアルンの森の踏破率100%で解放する。

分布を確認しやすくするため、通常の投入スタミナUIとは別に、同じ探索処理を1〜100回繰り返す検証用連続探索を用意している（15.19参照）。

HP0到達時は残りの探索処理単位を処理せず中断し、投入済みスタミナは返却しない。一次確率、相対weight、深度値、トラップ / 回復地点のHP量、ドロップランク率、素材テーブルはすべて **PROTOTYPE ASSUMPTION** である。

初期案の `+1 / +2 / +3` 等はHuman Verification前の1回限りのテンポ補正で4倍された。PR #36の実測（Issue #138以前の単一テーブル方式）では、スタミナ100あたりの平均深度進行は約28.0、HP0による中断割合は約87.8%であった。Issue #138で一次抽選方式へ変えたためこの実測値は現行構造の値ではない。本格バランスが確定したとは扱わない。

## 6. スタミナ

現在Prototypeのスタミナは最大値を持たず、世界開始日時からの経過時間で蓄積する（Issue #58）。現在値は保存せず、次式で算出する。

```text
現在スタミナ = 初期スタミナ + max(0, floor((現在時刻 - WORLD_OPEN_AT) / 1000)) × 回復速度 - 累計使用スタミナ
```

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. `WORLD_OPEN_AT` はPrototypeの固定設定値であり、プレイヤーの初回アクセス時に決めない
2. 初期スタミナは0、回復速度は現実時間1秒につき1とする
3. 最大値を設けず、100でも100,000でも上限なく蓄積する。オフライン中も経過時間として蓄積される
4. 探索イベント1回につき10を消費し、10 / 20 / 30 / 50から投入量を選べる
5. 通常操作で負数にならないよう、算出結果は0未満を返さない
6. プレイヤー状態は現在値ではなく累計使用スタミナ `staminaSpent` を保持する
7. `GAME_TIME_SCALE` とスタミナ回復速度は連動しない

Issue #87の検証条件として、投入したスタミナ1につき満腹度1を消費する（15.10参照）。投入したスタミナは探索開始時に全量コミットし、途中で中断しても未処理分を返却しない。

同じワールド・同じ時刻・同じ累計使用量であれば、参加日時にかかわらず同じスタミナになる。UIでは `⚡` と数値のみを表示し、最大値に対する割合バーは持たない。

旧仕様（最大100・1分1回復・現在値保存）からの移行では、保存値 `stamina` に `lastStaminaUpdate` からの未反映回復分（1分1回復、旧仕様の最大100で頭打ち）を加えた「旧仕様上の現在スタミナ」を求め、その値を維持するよう累計使用量を逆算する。移行が発生した場合はプレイヤーの操作を待たずに新形式でlocalStorageへ書き戻し、再読込時に再移行しないようにする。旧 `stamina` / `lastStaminaUpdate` / `worldStart` は読み込み時に破棄する。正式な最大値の有無、初期値、回復速度、投入上限は未決である。

## 7. ダンジョン深度・踏破率

アルンの森とゴブリンの巣穴はそれぞれダンジョン深度100を持つ。プレイヤー状態の `explorationDepth` はロケーション別のオブジェクトで、探索した現在地の値だけが進む（Issue #76）。踏破率は次式で算出する。

```text
踏破率(%) = explorationDepth[locationId] / locationDepth × 100
```

`explorationDepth` は個人の内部値でありUIへは表示しない。UI上の「踏破率」はロケーション別の共有踏破率 `worldState.locations[locationId].progress` を指す。旧保存データの単一 `explorationDepth`（旧「始まりの洞窟」の値）は引き継がず0で初期化する。深度値は **PROTOTYPE ASSUMPTION** である。

`explorationDepth` から算出する個人踏破率は個人の状態であり、Issue #56以降は通常画面へ表示しない。UIが「踏破率」として表示するのは共有進行値（15.3）であり、ボス討伐メニューの解放条件もこの共有進行値100%である。内部の `explorationDepth` は保持と加算を継続している。

正式設計では、ダンジョン探索進行をロケーション自身に紐づく全プレイヤー共有状態とし、UIでは「踏破率」のみ表示する。個人 `explorationDepth`／個人踏破率は本番モデルに持たない方向であり、本節は現行Prototypeの移行前状態を記録している。本IssueではコードとlocalStorage構造を変更しない。

## 8. 戦闘・育成・帰還・報酬

### 8.1 戦闘と育成

ターン制オートバトル、行動ごとの比率設定、物理ダメージ、DEX / AGI補正、会心を実装済みである。属性倍率と属性耐性へ対応し（Issue #67）、MPを検証用の戦闘リソースとして追加した（Issue #68）。アビリティからのスキル習得を接続し（Issue #71）、プレイヤー行動の選択方式として作戦型Utility AIを比較検証している（Issue #74）。

物理属性は斬 / 突 / 打、魔法属性は火 / 水 / 地 / 風 / 聖 / 闇を表現でき、攻撃に含まれる属性に対応する耐性だけを参照する。複数属性の倍率は単純加算して行動威力とし、対応耐性はIssue #129で攻撃内の属性構成比による重み付けへ変更した（15.16参照）。式は `GAME_DESIGN.md` 21.1 / 21.6 を正とする。

以下を **PROTOTYPE ASSUMPTION** として置いている。

- 旧 `action.power` は廃止し、その威力を属性倍率合計へ移行した。威力倍率と属性倍率の二重計上は行わない
- 新旧で式が異なるため、倍率は旧 `power` の写しではなく、属性耐性0の条件で旧式と同等のダメージになるよう再調整した

| 行動 | 旧 `power` | 新しい属性倍率 |
|---|---:|---|
| 通常攻撃 | 1.0 | 斬 1.00 |
| 強打 | 1.8 | 斬 1.42 |
| ひっかき | 0.5 | 斬 0.79 |
| 振り下ろし | 0.7 | 打 0.88 |
| 牙 | 0.8 | 突 0.91 |
| 急降下 | 1.2 | 打 1.09 |
| 体当たり | 0.6 | 打 0.92 |
| 包み込み | 1.0 | 打 1.00 |
| 殴打 | 0.8 | 打 0.91 |
| 兜割り | 1.2 | 斬 1.09 |
- Issue #125以降、プレイヤーの通常攻撃の属性配分は装備中武器から解決する。表の `斬 1.00` は既存短剣を装備した場合の値であり、行動データ側のフォールバック値でもある（15.15参照）
- 敵行動にも属性を割り当てた（ひっかき／兜割り＝斬、牙＝突、振り下ろし／急降下／体当たり／包み込み／殴打＝打）
- 全4種の敵が物理3属性・魔法6属性の耐性欄を持ち、洞窟スライムのみ斬耐性0.5、他はすべて0とした
- 耐性データが存在しない属性は0として扱う
- 魔法の計算基盤は実装済みだが、魔法を使う行動は存在しない。1つの行動は物理か魔法のどちらか一方として扱う
- 上記の再調整により、属性耐性0では旧式との基礎ダメージ差が各行動 ±0.2 以内（強打のみ最大 -3.2）に収まる
- 最大MPは固定50とし、正式な最大MP式やINT / MNDの寄与は実装しない
- 現行の仮行動「強打」は `mpCost: 10` とし、実行時にcurrent MPを消費する。1戦闘1回制限は維持する
- MP不足で強打を実行できない場合、Issue #74以降は行動選択の前に候補から除外する。Issue #68時点の「抽選後に通常攻撃へフォールバック」から仮採用を変更した。いずれの方式でもMPを負数にしない
- MP消費・候補除外の理由・戦闘終了時の残MPを戦闘ログで確認できる

STR / VIT / DEX / AGIへポイントを割り振ることができ、INT / MNDの戦闘効果は未実装である。

敵は次の4種を同一の戦闘エンジンで共通処理し、敵ごとに6基礎ステータス、行動、EXPを持つ。Lv / EXP、余剰EXP持越し、複数LvUP、旧名称のパラメータポイント／スキルポイントも保持する。

正式設計では、パラメータポイントをステータスポイント（SP）、スキルポイントをアビリティポイント（AP）へ整理し、「基本パラメータ → アビリティ → スキル」の育成構造を採用している。ただし、本IssueではPrototype実装を変更しないため、現状との差分は次の通りである。

- 保存データと実装上の変数名は旧 `parameterPoints` / `skillPoints` のままである。表示名のみIssue #56でSP（ステータスポイント）／AP（アビリティポイント）へ統一した
- SP相当の割り振りはSTR / VIT / DEX / AGIのみ実装済みで、INT / MNDは未実装である
- AP1消費によるアビリティLv上昇と、規定Lv到達によるスキル自動習得を実装済みである（Issue #71）。検証用にアビリティ1種・アクティブスキル1種のみを対象とする
- アクティブ／リアクション／トリガー／パッシブのスキル分類は未実装である
- 「強打」は最初から使える仮行動ではなく、アビリティから習得するPrototype検証用のアクティブスキルである。名称・性能・習得条件はいずれもPROTOTYPE ASSUMPTIONであり、正式スキルとして確定していない

#### アビリティとスキルの最小縦切り（Issue #71）

```text
探索 → EXP → LvUP → AP +1 → APを1消費 → 斬撃術 Lv0 → Lv1 → 強打を自動習得
→ 戦術設定へ強打を追加 → MPと属性を使ってオートバトル
```

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. アビリティは「斬撃術」1種のみ。Prototypeでの上限はLv1であり、正式なアビリティ最大Lvではない
2. 斬撃術Lv1で「強打」（Active / 斬1.42 / MP10 / 1戦闘1回）を自動習得する
3. スキル習得状態は二重管理せず、アビリティLvから導出する
4. 未習得のあいだ強打は戦術設定にも行動候補にも現れない。Issue #71時点の初期比率は通常攻撃100%だったが、Issue #74で検証用回復行動を追加したため現在は通常攻撃75% / 応急手当25%である
5. 習得直後の初期比率は通常攻撃60% / 強打20% / 応急手当20%とし、以後はプレイヤーが変更できる（Issue #71時点は通常攻撃60% / 強打40%）
6. アビリティLvは `state.abilities` へ保存する。旧セーブにデータがない場合はLv0で補完する
7. 旧セーブの戦術設定に未習得スキルの使用率が残っていても、利用可能行動だけで再構成し実行しない
8. アビリティLvは自動上昇せず、APをどのアビリティへ使うかはプレイヤーが選択する
9. スキル装備枠／セット枠は設けず、「習得済みアクティブスキルが戦術設定に現れる」ことを最小の使用スキル設定として扱う
10. Issue #131でアビリティへ基礎パラメータ条件を持たせ、斬撃術は検証用に `基礎DEX 8以上` を条件とした。判定は装備補正を含まない基礎値だけで行う（15.17参照）。初期DEXが8のため、通常の初期プレイでは従来どおりLvを上げられる

| 敵 | 枠 | Prototype上の役割 |
|---|---|---|
| ゴブリン | 通常敵 | 比較的安全な基準敵 |
| 洞窟コウモリ | 通常敵 | ゴブリンより危険 |
| 洞窟スライム | 通常敵 | 低火力・高耐久寄り |
| 洞窟オーク | 強敵 | 「強敵遭遇」イベント専用。高リスク高成果 |

通常敵は「通常敵遭遇」から、洞窟オークは「強敵遭遇」から出現し、遭遇プールを分けている。各敵のHP、能力値、行動威力、EXPはいずれも **PROTOTYPE ASSUMPTION** であり、正式仕様として扱わない。洞窟スライム / 洞窟オークはPR #36で追加した仮値である。属性倍率と属性耐性はIssue #67で追加した。状態異常・特殊技・複数体戦闘は追加していない。

PR #20 / #22の実測では、ゴブリン / 洞窟コウモリについて、敵によってDEX / AGIの効き方が異なる一方、STR / VITは両敵に対して依然として強く、敵ごとに最適育成が完全に分かれる段階には至っていない。正式バランスの確定ではなく、差分型ダメージ式の成長曲線は今後の課題である。

洞窟オークのみ、通常敵AIとして最小Utility AIを適用している（Issue #48）。共通評価関数 `utilityScore` が敵ごとの `ai` 設定（各行動の `baseScore` / `targetLowHpBonus` / `selfLowHpBonus` と `thresholds.targetLow` / `selfLow`）を参照し、現戦況（自HP率とプレイヤーHP率）からScoreを計算して最大値の行動を選ぶ。同点時は行動リストの先頭側を優先する。洞窟オークの性格は「相手を仕留めに行く／追い詰められた時に強行動を選ぶ」を1案に固定し、通常時は殴打、プレイヤーHPが低い時または自HPが低い時に兜割りへ切り替わる。Score値・閾値はすべて **PROTOTYPE ASSUMPTION** である。ゴブリン / 洞窟コウモリ / 洞窟スライムは比較のため従来の固定確率行動を維持している。AI設定は現段階では単一HTMLの `CONFIG` 内に置き、外部JSON化は行っていない。

#### プレイヤー作戦型Utility AIの比較検証（Issue #74）

回復や防御のような行動が増えると、使用率だけの確率抽選では戦況を無視した行動選択になりうる。そこで、プレイヤーが戦闘方針（作戦）を選び、戦況に応じて行動を評価する方式が自動戦闘に適するかを比較検証する。**正式採用ではなく、Human Verification後に本線で判断する。**

```text
作戦を選ぶ → 実行不能な行動を候補から除外 → 残りをUtility評価 → 上位候補から選択
```

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. 作戦は「バランス」「攻撃重視」「生存重視」の3種のみ。正式な作戦種類・名称・数ではない
2. 検証用の回復行動「応急手当」（HP回復35 / MP12 / 習得条件なし）を追加した。アビリティ・AP・スキル習得処理を経由しないPrototype専用の検証用Active行動であり、正式スキルではない。習得stateも追加していない
3. 実行不能な行動はUtility評価の前に候補から除外する（基礎優先度0 / 未習得 / MP不足 / 1戦闘の使用回数上限到達 / HP満タン時の回復）
4. **基礎優先度0はPrototypeでは使用禁止として扱う。** 0を指定した行動は戦況に関わらず候補へ出さず、生存重視でHPが危険域にあっても応急手当0なら使用しない。除外が重なって候補が全滅した場合のみ、安全策として通常攻撃へフォールバックする（戦闘ログに「全候補除外のため通常攻撃へfallback」と表示する）。戦術設定は合計100%を要求するため、通常はUIから全候補0へ到達しない
5. 現行の使用率は廃止せず、「基礎優先度（使用傾向）」として再解釈してScoreの基礎評価へ用いる。合計を100%にする制約と入力UIは維持する
6. Scoreは次の構成とする。式・補正値・閾値はすべて仮値である

   ```text
   Score = 基礎優先度 + 戦況評価 + 作戦補正 - リソース消費ペナルティ

   戦況評価              回復は自HP率が低いほど加点、攻撃は敵HP率が低いほど加点
   作戦補正              回復 / MP消費スキル / 通常攻撃の役割ごとに加点・減点
   リソース消費ペナルティ  MPコスト × MP消費率 × 作戦ごとの係数
   ```

7. MP残量を行動評価へ利用する。攻撃重視はMPを使いやすく、生存重視は回復のためにMPを温存する
8. 完全決定論にせず、最高Scoreとの差が `randomBand`（仮値10）以内の上位候補だけを抽選対象とする。Scoreが離れた候補は選ばれない。抽選は一様ではなく、最高Scoreに近い候補ほど選ばれやすい重み付き抽選とする

   ```text
   weight = randomBand + randomWeightBase - (最高Score - その候補のScore)
   randomBand = 10、randomWeightBase = 1（いずれも仮値）
   ```

   band内の候補は必ず `randomWeightBase` 以上の重みを持つ。例えばScore差5の候補は重み6、最高Scoreの候補は重み11となり、約6:11の比率で選ばれる。`randomBand` を0にすると抽選そのものを行わず決定論になり、同点時は行動リストの先頭側を優先する
9. 作戦は `state.strategy` へ保存する。旧セーブに作戦がない場合と未知IDの場合は、いずれも「バランス」で補完する
10. 敵Utility AI（Issue #48）とはScore式もAI設定も共通化していない。共有するのは「実行可能な候補を評価して選ぶ」という考え方までである。属性ダメージ式、MP式、敵行動、敵AIのScoreは変更していない

作戦による行動選択の違いは次のとおりである（基礎優先度は通常攻撃60 / 強打20 / 応急手当20、敵HP満タン、`randomBand` 0での確認値）。

| 戦況 | バランス | 攻撃重視 | 生存重視 |
|---|---|---|---|
| HP100% / MP100% | 通常攻撃 | 強打 | 通常攻撃 |
| HP75% / MP100% | 通常攻撃 | 強打 | 応急手当 |
| HP30% / MP100% | 応急手当 | 強打 | 応急手当 |
| HP100% / MP20% | 通常攻撃 | 強打 | 通常攻撃 |

作戦方式を正式採用するか、使用率方式を廃止するか、優先度／使用傾向方式を正式採用するかはいずれも未決であり、`OPEN_QUESTIONS.md` 4.1 へ整理している。

### 8.2 HP / MP持越しと宿屋

`currentHp` と `currentMp` を保持し、戦闘終了時のHP / MPを次戦へ持ち越す。勝利後も自動回復しない。HP0では探索不可だが街へ帰還でき、街へ移動しただけではHP / MPとも回復しない。街の無料宿屋で最大HP / MPまで回復する。MPが存在しない旧セーブは最大MPで補完する。

Issue #87の検証条件として、通常探索中の戦闘終了後にかぎり、満腹度を消費してHP / MPを回復する（15.10参照）。宿屋は満腹度を回復しない。

固定最大MP、無料宿屋でのHP / MP全回復、HP0、死亡・ロストなしの扱いは **PROTOTYPE ASSUMPTION** である。MPがオートバトルへ必要か、HPとMPが単なる二重の帰還制約にならないかはHuman Verification対象とする。

## 15. 現行Prototypeで置いている最小仮定

### 15.1 ショップ・装備

最小ショップと装備変更はPR #30で実装済みであり、以下を **PROTOTYPE ASSUMPTION** として置いている。

1. 「訓練用の短剣（ATK 11）」「旅人の服（DEF 11）」を初期所持・初期装備とする
2. 旧保存データではスターター装備を安全に補完する
3. 購入候補は「鉄の短剣（ATK 13、15 Gold）」「革の鎧（DEF 13、15 Gold）」を各1種類とする。Issue #125で通常攻撃属性の検証用に「ブロンズソード（ATK 12、150 Gold）」を武器の購入候補へ1本追加した（15.15参照）。Issue #131では装備パラメータ補正の検証用に「マジックソード（ATK 25、2200 Gold、DEX+2）」をさらに1本追加した（15.17参照）
4. 街でのみ購入でき、Gold不足・購入済みの場合は購入できない
5. 重複所持はせず、購入だけでは自動装備しない
6. 所有装備から武器・防具を各1つ装備し、スターター装備へ戻せる
7. 所有・装備状態をlocalStorageへ保存し、不正IDはスターター装備へフォールバックする

```text
攻撃値 = STR + 現在武器の実効ATK
防御値 = VIT + 現在防具の実効DEF
```

Issue #102で装備強化をPrototypeへ追加したため、戦闘へ渡す武器ATK / 防具DEFは強化値を反映した実効値である（15.12参照）。強化していない装備では基礎性能と一致する。

価格・性能は反復調整しない。本格装備・経済仕様は確定していない。

### 15.2 ゲーム内日時

ゲーム内日時はPR #32で実装し、Issue #58で表示粒度と起点を更新した。ヘッダーに表示専用として表示する。以下は **PROTOTYPE ASSUMPTION** である。

1. 現実時間の100倍で進行する（`GAME_TIME_SCALE = 100`）
2. 1年365日、1ヶ月28日、13ヶ月の独自暦と7曜日を保持し、年末の1日は「竜触の刻」として扱う
3. 起点はプレイヤーごとの `worldStart` ではなく、ワールド共通の設定値 `WORLD_OPEN_AT` とする。旧セーブの `worldStart` は読み込み時に破棄する
4. 通常日の表示は月名・第何週か（1〜4）・曜日のみとする。週番号は1か月28日を7日ずつ区切って算出する
5. 年、月内の具体的な日付、時刻は内部計算として保持するが、通常画面へ表示しない
6. 特別日は月・週・曜日の代わりに「竜触の刻」だけを表示する
7. 現時点では表示のみで、探索、戦闘、ショップ等へのゲーム効果を持たない。スタミナ回復速度とも連動しない

暦の算出は現在時刻を注入できる関数 `calendarParts(now)` に寄せ、固定時刻での自動確認を可能にしている。「竜触の刻が内部的な曜日周期を1日進めるか」は既存の未決事項のままである。

オンライン実装時の時間進行方式、サーバー時刻との同期、時間帯によるゲーム効果は未決であり、ここでは正式化しない。

### 15.3 世界共通進捗のローカルモック

単一プレイヤーの探索成果を世界全体の探索成果として扱うローカルモックは、Issue #44で実装済みである。

```text
世界共通クエストを確認
↓
探索する
↓
ローカル上の世界共通進捗が増える
↓
100%到達
↓
ボスメニューが1回だけ解放
↓
100%済みロケーションにも引き続き入り、通常探索できる
```

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. `worldState`（世界共通進捗、クエストStep、階層ボス解放状態）を、プレイヤー状態とは別のlocalStorageキーへ保存する
2. 個人の `explorationDepth`／個人踏破率とは別概念として保持し、同一値として扱わない
3. 探索イベントで得た深度進行量を、そのまま世界共通進捗への仮加算量として利用する
4. 世界共通進捗は100%を上限とし、100%を超えて保持しない
5. 世界共通進捗100%で階層ボスを解放し、解放処理は1回だけ成立する
6. 100%到達後も通常探索・戦闘・素材収集を継続でき、世界共通進捗は100%から増加しない
7. クエストタイトルと本文は固定データで、100%到達後にボス発見済みの文へ切り替える。ゲーム実行中に生成AI APIを呼び出さない

Issue #56以降、この共有進行値はUI上「踏破率」として表示する（15.4）。Issue #76で状態をロケーション単位へ分割し、内部の状態名は `worldState.locations[locationId].progress` になった。加算方法と100%到達で1回だけ解放が発火する扱いは変更していない。

単一プレイヤーの探索を世界全体の成果とみなす点、および加算量そのものが仮であり、本番の世界進捗加算方式ではない。本番のオンライン共有DB、バックエンド、複数プレイヤーの同時更新・排他制御は実装していない。必要探索量と個人貢献も確定していない。

Issue #76で、共有踏破率・ロケーションアンロック・クエストStep・ボスアンロック／撃破・第2層アンロックを別状態として保持する構造へ移行した（15.7）。個人 `explorationDepth` もロケーション別に分割済みである。

### 15.4 通常画面のUI構造

Issue #56で、`GAME_DESIGN.md`「25. UI・情報表示の優先順位」の領域分担を現行Prototypeへ実装した。共同開発者の `prototype_updated.html` はレイアウト／情報階層の参照資料として使用し、コードの基準は最新 `main` の `prototype.html` とした。

ヘッダー：ゲーム内暦（月 / 第何週 / 曜日）/ スタミナ（⚡と数値）/ 現在階層 / 現在地 / 踏破率（ダンジョンのみ）
ヘッダー直下：第1層ラベル ＋ 階層内のロケーション移動（どこへ行くか）

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. ヘッダーの階層表示は `現在階層` と呼び、プレイヤーが現在いる階層を指す。世界全体の最新攻略階層ではない
2. 世界全体の最新攻略階層に対応する状態は保持しておらず、Prototypeでは表示しない
3. ダンジョン滞在時のみ、**現在地の**共有踏破率 `worldState.locations[locationId].progress` を「踏破率」として表示する。街では表示しない
4. 右カラムは `details` 要素の開閉式パネル（ステータス / アビリティ / スキル / 所持品）と、その下に常時表示するロケーションメニューで構成する。右カラム全体を切り替える `activeView` は持たない（Issue #60）
5. SPはステータスポイント、APはアビリティポイントとして表示し、Lv付近で未使用分を確認できる
   - MPはIssue #68でHPと同様に現在値 / 最大値のバーとして追加した。表示と値はMPの正式採用を意味しない
6. スタミナは最大値を持たないため、ヘッダーでは `⚡` と現在値のみを表示し、割合バーを持たない。探索の投入量ボタンも `⚡10` 形式で表記する（Issue #58）
7. 情報パネルは初期状態ですべて閉じ、開閉状態はlocalStorageへ保存しない。再読込時はすべて閉じた状態から開始する
8. Prototypeでは複数の情報パネルを同時に開ける（案A）。1つ開いたら他を閉じる排他方式（案B）とするかはHuman Verification後に判断する
9. 左カラムのショートカットは右カラムを切り替えず、対象パネルを開いてその位置までスクロールする。他の開いているパネルは閉じない
10. 「現在地の行動」は踏破率に関係なく常時表示する。街は宿屋 / よろず屋 / 酒場、ダンジョンは探索 / 討伐 / 採取を並べ、宿屋・よろず屋・探索は現行機能へ接続する。酒場・討伐・採取はUI候補としてdisabled表示に留め、ゲームロジックを実装しない
11. ヘッダー直下の領域は「階層とその階層内のロケーションを選択する領域」として扱い、左ラベルを機能名ではなく階層名「第1層」とする（Issue #61）。Prototypeは第1層のみを扱うため階層選択は実装せず固定表示とし、右側のロケーション一覧と移動処理は現行実装のままとする
12. ロケーション移動はヘッダー直下へ集約し、街本文の「ダンジョンへ」とダンジョン本文の「街へ戻る」は削除した（Issue #64）。移動処理 `move()` 自体は再利用している
16. 未解放ロケーションは非表示にせず、**disabled表示**で常時並べる（Issue #76の仮採用）。鍵アイコンと `title` / `aria-label` に解放条件を示し、押しても移動しない。「次に何をすればよいか」を移動バーだけで把握でき、解放の瞬間も同じ位置で認識できることを優先した。非表示／ロック表示との比較はHuman Verification後に判断する
13. 「現在地の行動」の行動ボタンは、ページ内スクロールではなくその領域内の表示内容を切り替える。上部の情報パネルの開閉状態には影響しない
14. 行動の選択状態はメモリ上のみで保持し、localStorageへ保存しない。街へ移動した直後は宿屋、ダンジョンへ移動した直後は探索を初期選択とする。再読込時も現在地に応じた既定から開始する
15. 探索実行後も選択中の行動は探索のままとし、探索結果・戦闘ログ・報酬を同じ領域で確認できる

### 15.7 第1層Prototype進行モデル

**Prototype実装済み／各名称・数値は仮値**

Issue #54で整理した第1層の進行モデルを、Issue #76で `prototype.html` へ接続した。「探索 → 世界変化 → 次の目標 → ボス → 次階層」という基本サイクルを検証する骨格であり、第1層固有の名称や条件を全階層共通仕様として固定するものではない。第1層の中身を増やすことは本モデルの目的ではない。

#### ロケーションと開始状態

| 種別 | 名称 | Prototype開始時 |
|---|---|---|
| 街 | はじまりの街 アルマセント | 解放済み |
| ダンジョン | アルンの森 | 解放済み |
| ダンジョン | ゴブリンの巣穴 | 未解放 |

開始時の進行中クエストは「アルンの森を調査せよ」とする。開始時点ではゴブリンの巣穴へ移動できない。未解放ロケーションは **disabled表示** で常時並べ、鍵アイコンと解放条件を示す（Issue #76の仮採用）。非表示・ロック表示との比較はHuman Verification後に判断する。

#### 基本攻略サイクル

```text
はじまりの街 アルマセント
↓
「アルンの森を調査せよ」進行中
↓
アルンの森を共同探索
↓
アルンの森 踏破率100%
↓
「アルンの森を調査せよ」完了
↓
「ゴブリンを掃討せよ」開始
↓
ゴブリンの巣穴 解放
↓
ゴブリンの巣穴を共同探索
↓
ゴブリンの巣穴 踏破率100%
↓
「ゴブリンを掃討せよ」のStep更新
↓
ゴブリン・ウォーロード 解放
↓
ゴブリン・ウォーロード撃破
↓
「ゴブリンを掃討せよ」完了
↓
第2層への移動解放
```

各遷移は条件成立時に1回だけ発火する。アルンの森とゴブリンの巣穴はそれぞれ独立した共有踏破率を持ち、100%到達後も通常探索を継続できる。

「ゴブリンを掃討せよ」は巣穴探索とボス撃破を別クエストへ分割せず、1つの世界共通クエスト内で次のようにStepを進める。

```text
Step 1：ゴブリンの巣穴を調査する
↓ 巣穴 踏破率100%
Step 2：ゴブリン・ウォーロードを討伐する
↓ ボス撃破
クエスト完了
```

クエスト本文、NPC台詞、詳細な演出文は確定しない。ゴブリン・ウォーロードについても、第1層の世界進行上でアンロック状態と撃破状態を持つことだけをこのモデルで定める。ステータス、スキル、AI、ギミック、戦闘形式、参加人数、開始方法、報酬、再戦可否は未決である。

ボス撃破後は「ゴブリンを掃討せよ」の完了と第2層への移動解放を1回だけ発火する。第2層の街、ダンジョン、クエスト、敵、コンテンツ名、開始状態は本モデルの対象外であり、第2層そのものは実装しない。

#### 状態の責務

第1層の進行を単一の `progress` や `step` へ集約せず、少なくとも次を別状態として扱う。

```text
worldState
├ locations
│  ├ forest
│  │  ├ unlocked
│  │  └ progress
│  └ cave
│     ├ unlocked
│     └ progress
├ quest
│  ├ currentQuest
│  └ step
├ bosses
│  └ goblinWarlord
│     ├ unlocked
│     └ defeated
└ layers
   └ layer2Unlocked
```

これは責務分離を説明する概念例であり、正式なJavaScriptオブジェクト構造や変数名を固定しない。特に、森の踏破率、巣穴の踏破率、クエスト状態／Step、ロケーションアンロック、ボスアンロック、ボス撃破、第2層アンロックを同一状態にしない。

#### Prototypeの実装（Issue #76）

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. ロケーションIDは `town`（アルマセント）／ `forest`（アルンの森）／ `den`（ゴブリンの巣穴）とする。旧「始まりの洞窟」の `cave` は再利用していない。旧セーブの `location:'cave'` がlockedであるはずの巣穴へ暗黙にマッピングされる事故を避けるためである
2. `worldState` は概念例どおり `locations` / `quest` / `bosses` / `layers` を別状態として保持する。ロケーション別の共有踏破率は `worldState.locations[id].progress`、アンロックは同 `.unlocked` である
3. 各遷移は条件成立時に1回だけ発火する。`unlockLocation()` / `unlockBoss()` / `defeatBoss()` はいずれも成立済みなら `false` を返して何も変更しない
4. 踏破率100%到達後もそのロケーションで探索を継続できる。加算量が0になるだけである
5. 個人の `state.explorationDepth` もロケーション別のオブジェクトへ分割した。UIへは表示せず、デバッグ操作でのみ確認できる
6. 戦闘報酬テーブルはロケーション単位（`forest` / `den`）へ分けている。Issue #78で両者へ別テーブルを割り当てた（15.8 参照）
7. ゴブリン・ウォーロードはIssue #105で実際のボス戦へ置き換えた。解放後に挑戦し、勝利した場合だけ撃破・クエスト完了・第2層解放が成立する（15.13参照）
8. 第2層はIssue #111で階層遷移まで実装した。`worldState.layers.layer2Unlocked` は世界進行上の解放状態、`state.layer` は現在プレイヤーがいる階層として別に保持する。第2層のロケーション・敵・クエスト・世界設定は未実装で、遷移検証用のplaceholderのみを置いている（15.14参照）
9. クエストは「アルンの森を調査せよ」→「ゴブリンを掃討せよ」（Step: 巣穴調査 → ウォーロード討伐）→ 完了 の順に進み、完了したクエストIDは `worldState.quest.completed` へ積む

#### 旧セーブからの移行

旧形式の世界進行（`locations` を持たず単一 `progress` を持つ形式）は **引き継がず破棄し、新形式で初期化する**。不明瞭な自動変換で正式な第1層進行を飛ばさないためである（Issue #76 §9）。

- 破棄した場合はシステムログへ「旧形式の世界進行を検出したため、第1層の進行を初期化した」と明示し、無操作でも新形式を書き戻す
- 個人データ（Lv / EXP / SP / AP / stats / HP / MP / Gold / items / equipment / tactics / abilities / strategy）はすべて保持する
- 旧 `state.location`（`'cave'` を含む未知IDと未解放ロケーション）はアルマセントへ正規化する
- 旧 `state.explorationDepth`（単一値）は引き継がず、ロケーション別に0で初期化する

### 15.8 第1層ロケーションの最小コンテンツ差（Issue #78）

アルンの森とゴブリンの巣穴を、背景画像なしでも別ロケーションだと分かる最小限まで差別化した。差別化するのは **通常敵・強敵・探索イベント・戦闘報酬の4種類だけ** で、ダメージ式、Ability / Skill、MP、作戦型Utility AI、敵Utility AI、状態異常、第1層の解放条件、正式ボス戦は変更していない。

#### データ構造

ロケーション別の内容は `CONFIG.locations.content[ロケーションID]` へ集約し、呼び出し側でロケーション判定を分岐させない。

```text
CONFIG.locations.content[id]
├ normalEnemies      通常敵の出現率（敵IDと確率のみ）
├ eliteEnemies       強敵の出現率（敵IDと確率のみ）
├ explorationEvents  探索イベントテーブル
└ rewards.itemDrops  戦闘勝利時のアイテム報酬テーブル
```

敵のステータス・行動・耐性は従来どおり `CONFIG.battle.enemies` / `CONFIG.battle.eliteEnemies` のマスタ定義だけに置き、ロケーション側は出現率のみを持つ。外部JSON化は行っていない。

#### 通常敵・強敵

| ロケーション | 通常敵（出現率） | 強敵 |
|---|---|---|
| アルンの森 | フォレストウルフ 35% / ワイルドボア 30% / キラービー 25% / ゴブリン 10% | アルファウルフ |
| ゴブリンの巣穴 | ゴブリン 50% / 洞窟コウモリ 30% / 洞窟スライム 20% | 洞窟オーク |

アルンの森は生活圏に近い森として野生動物・昆虫を主敵とし、ゴブリンは「森へ入り込んでいる」低頻度の敵として残す。ゴブリンの巣穴はゴブリンを最も高頻度にした拠点型の洞窟とする。アルファウルフは森側の強敵として追加した新規敵であり、既存の洞窟オークと同じ形式のUtility AI設定を持つ（AIの仕組み自体は変更していない）。出現率・ステータス・行動値はすべて **PROTOTYPE ASSUMPTION** である。

#### 探索イベント・戦闘報酬

探索イベントテーブルは 5.1 のとおりロケーション別である。森には自然素材の採取、人の利用痕跡、ゴブリンの痕跡を、巣穴には盗品・ガラクタ、粗雑な罠、拠点痕跡を置いた。痕跡系イベントは深度を進めるだけで、解放条件やクエストへは接続していない。

戦闘勝利時のアイテム報酬は次のとおりで、森と巣穴で同一テーブルを使わない。

| ロケーション | アイテム報酬 |
|---|---|
| アルンの森 | 薬草 40% / アルンベリー 30% / 獲得なし 30% |
| ゴブリンの巣穴 | 古い硬貨 30% / 鉄鉱石 25% / ゴブリンの牙 20% / 獲得なし 25% |

固有素材（敵ドロップ）は 8.3 のとおり敵単位のままである。森の敵素材が巣穴で出ないこと、巣穴の敵素材が森で出ないことは `scripts/check_prototype_behavior.js` で検証している。

### 15.9 強敵単体と長期探索の検証手段（Issue #80）

| 操作 | 内容 |

| HP / MPを全回復 | 検証を毎回同じ条件から開始するための回復。街以外でも使える |

### 15.10 満腹度による戦闘間回復（Issue #87）

**確定度：Prototype仮採用（検証用）**

Issue #80 / PR #81のHuman Verificationで、強敵単体の強さよりも戦闘間の継戦手段不足が主要因と判断したため、満腹度を「複数戦闘をまたぐ長期探索リソース」としてPrototypeへ最小導入した。このIssueでも敵能力値、ダメージ式、Skill性能、探索イベント確率、スタミナ投入候補は変更していない。

以下はすべて **PROTOTYPE ASSUMPTION** であり、正式仕様ではない。Human Verification前に `GAME_DESIGN.md` へ昇格しない。

#### 満腹度state

- プレイヤーstateは現在満腹度 `satiety` のみを保持する
- 最大満腹度は保持せず、次式で導出する

```text
最大満腹度 = (最大HP + 最大MP) × 10
```

- 倍率10はPrototype仮値である
- 満腹度を持たない旧セーブは、読み込み時に現在満腹度＝最大満腹度で補完する
- 現在満腹度は0未満にせず、最大満腹度を超えて保持しない
- 最大HP / MPが変化した場合の正式な満腹度挙動は未決であり、このIssueでは育成仕様を追加していない

#### 消費と回復

| 契機 | 満腹度の増減 |
|---|---|
| 探索開始（スタミナ投入） | 投入スタミナ1につき満腹度1を消費する |
| 通常探索中の戦闘終了後 | 不足HP + 不足MP を必要満腹度として消費し、HP / MPを回復する |
| 街の検証用補給 | 最大満腹度まで戻す |

戦闘後回復は勝敗を問わず行う。

```text
必要満腹度 = (最大HP - 現在HP) + (最大MP - 現在MP)
```

満腹度が必要量以上ある場合はHP / MPを最大まで回復し、実際に回復したHP + MPと同量の満腹度を消費して探索を続行する。

満腹度が不足する場合は、残っている満腹度だけを不足HP : 不足MPで比例配分して部分回復し、その時点で探索を中断する。端数はHP側を切り捨て、余りをMPへ回す決定論的な処理とし、回復量合計は使用満腹度と一致する。

```text
例：不足HP 40 / 不足MP 30（必要満腹度 70）で満腹度 35
→ HP +20 / MP +15 / 満腹度 0 → 探索中断
```

比例配分・端数処理はPrototype検証用の初期案であり、HP優先等の正式方式は決めていない。

#### 中断条件と敗北の扱い

- 戦闘後にHP / MPを最大まで回復できた場合は探索を続行する
- 満腹度不足で最大まで回復できなかった場合は、部分回復後に探索を中断する
- 戦闘敗北そのものは探索終了条件にしない。勝敗（報酬・探索進行）と継戦可否を分離する
- 敗北時は従来どおり勝利相当のEXP / 戦利品 / 踏破率加算を与えない
- HP0による中断（トラップ等）は従来どおり残る
- 中断しても投入済みスタミナは返却しない

「敗北後に回復して探索を続行できること」が自然かはHuman Verification対象であり、死亡・戦闘不能・敗北ペナルティの正式仕様は追加していない。

#### 強敵直接テストとの分離

15.9の強敵直接テスト（アルファウルフ／洞窟オークとの直接戦闘）は、探索中の蓄積ダメージと強敵単体の強さを分離するための検証機能である。満腹度による戦闘間回復は通常探索中の戦闘にのみ適用し、直接戦闘へは適用しない。直接戦闘は満腹度を消費せず、戦闘後回復も行わない。

#### 検証用補給

街の画面へ「満腹度を補給（検証用）」を追加し、満腹度を最大まで戻せるようにした。Prototype検証専用の手段であり、宿屋・食事・料理・食料アイテム・Gold・生産のいずれとも接続していない。無料宿屋はHP / MPのみを回復し、満腹度を回復しない。

#### ログ

戦闘後ログと「今回の探索結果」で次を確認できる。

- 戦闘終了時のHP / MP
- 不足HP / 不足MPと必要満腹度
- HP回復量・MP回復量・満腹度消費量
- 回復前／回復後の満腹度
- 全回復できたか、満腹度不足で中断したか

継戦性サマリーへの追加項目は15.9に記載している。

#### 検証補助

`scripts/simulate_endurance.js` で、投入スタミナ10 / 20 / 30 / 50を複数回試し、イベント数・戦闘回数・勝敗・中断率・満腹度残量の傾向を確認できる。合否判定は行わず、期待する結果へ合わせるための数値調整も行わない。

#### このIssueで判断しないこと

満腹度の正式採用可否、最大満腹度式と倍率、戦闘後回復を勝敗共通にするか、満腹度不足時の配分方式、スタミナ消費で満腹度を減らすか、中断時の未処理スタミナ、街での補給手段の接続先は、いずれもHuman Verification後に判断する。`OPEN_QUESTIONS.md` 2.1 / 3.2 / 4.5 / 4.6 / 4.8 の回答はこのIssueでは確定させない。

### 15.12 装備強化のGold再投資（Issue #102）

**確定度：Prototype仮採用（検証用）**

Issue #99 / #101で整理した装備育成循環のうち、**強化だけ**を縦切りしてPrototypeへ追加した。Goldを装備へ再投資して戦力を伸ばす体験が成立するかを確認するための最小実装であり、OP・鍛造・調律・共鳴・分解・レアリティ・同一装備の複数個体・装備ドロップは実装していない。

以下はすべて **PROTOTYPE ASSUMPTION** であり、数値と確率方式を正式仕様にはしない。

#### 強化値と実効性能

- 対象は現行Prototypeの全装備（訓練用の短剣・鉄の短剣・旅人の服・革の鎧。Issue #125でブロンズソード、Issue #131でマジックソードを追加した）
- 強化は基礎性能（武器ATK / 防具DEF）だけへ作用し、装備パラメータ補正は増幅しない（15.17参照）
- 強化値は `+0` 〜 `+10`
- 同一装備を複数所有しないため、強化値は装備ID単位で保持する（装備インスタンスモデルは作らない）

```text
実効装備性能 = round(基礎性能 × (1 + 強化値 × 0.1))
```

武器は基礎ATK、防具は基礎DEFへ適用し、`+10` で基礎性能の200%になる。実効値は既存のダメージ計算経路（`攻撃値 = STR + 武器ATK` / `防御値 = VIT + 防具DEF`）へそのまま渡す。ダメージ式・敵能力・Skill倍率・満腹度は変更していない。

#### 確率成功方式

| 強化 | 成功率 | | 強化 | 成功率 |
|---|---:|---|---|---:|
| +0 → +1 | 50% | | +5 → +6 | 5% |
| +1 → +2 | 40% | | +6 → +7 | 4% |
| +2 → +3 | 30% | | +7 → +8 | 3% |
| +3 → +4 | 20% | | +8 → +9 | 2% |
| +4 → +5 | 10% | | +9 → +10 | 1% |

失敗しても **装備消失なし・強化値低下なし** で、Goldだけを消費する。確率方式そのものが有効かはHuman Verification対象であり、確定強化・天井付き方式との比較は行っていない。

#### 費用と連続鍛錬

- 1試行 = 1 Gold（Layer1経済とレアリティが未確定のため、操作と確率体験を切り出すための仮値）
- 1 / 10 / 50 / 100回の連続鍛錬を選べる
- 1試行ずつ順に処理し、**指定回数到達・+10到達・Gold不足**のいずれかで停止する
- Goldは先払いせず、**実際に実行した試行分だけ**消費する
- +10の装備は実行できない（試行もGold消費も発生しない）

#### UI

街の行動へ「鍛冶屋」を追加し、本Issueでは強化だけを操作できる。鍛造・調律・共鳴・分解は未実装ボタンとしても並べない。

鍛冶屋で確認できる情報：対象装備名、現在強化値、基礎ATK / DEF、強化後の実効ATK / DEF、現在段階の成功率、1試行のGold費用、所持Gold、1 / 10 / 50 / 100回の実行導線、直近の実行結果（試行数・成功数・失敗数・Gold消費・開始強化値→終了強化値・停止理由）。実行結果はシステムログにも残る。直近の実行結果は表示専用であり、localStorageへ保存しない。

冒険者情報とよろず屋の装備一覧にも、強化値と実効性能を表示する。

#### 検証用Gold

デバッグ領域へ「検証用 Gold +1000」を追加した。Human Verification用であり、ゲーム内の正式なGold供給源ではない。デバッグGoldを使うため、このIssueでは正式なGold獲得量との釣り合い、レアリティ別費用、経済全体の吸収量は評価しない。

#### 旧セーブ互換

強化情報を持たない旧セーブは全所持装備 `+0` として読み込み、装備所持・装備中状態は保持する。未知の装備IDと不正値（負数・非整数）は保持せず、最大値を超える値は `+10` へ丸める。プロトタイプ初期化では強化値も初期化する。

#### このIssueで判断しないこと

確率成功方式の継続可否、確定強化／天井付き方式との比較、成功率・費用・性能倍率の正式値、分解による投資回収を独立Prototypeにするか、ショップ価格・素材売価・Gold流通量の再調整は、Human Verificationの結果を見て判断する。

### 15.14 第2層への最小遷移（Issue #111）

**確定度：Prototype仮採用（検証用）**

第2層のコンテンツを作らず、1階層前提で作ってきた状態モデルとUIが2階層でも成立するかを検証するための最小実装である。第2層の街・ダンジョン・敵・ボス・クエスト・素材・世界設定・バランスはいずれも実装していない。

#### 状態

次の3つを混同せずに保持する。

| 状態 | 保持先 | 意味 |
|---|---|---|
| 世界進行上の解放状態 | `worldState.layers.layer2Unlocked` | ゴブリン・ウォーロード撃破で `true` になる |
| 現在プレイヤーがいる階層 | `state.layer` | 既定は第1層。第2層へ移動すると2になる |
| 現在ロケーション | `state.location` | 現在階層に属するロケーションのみを取る |

- 各階層は入口ロケーション（`CONFIG.layers[].entry`）を明示し、「ロケーション配列の先頭が入口」という暗黙依存を作らない
- 未解放の階層・不正な階層値は第1層へ正規化し、現在階層に属さないロケーションはその階層の入口へ落とす
- 100層分の正式なマスターデータとstate構造は本Issueで設計しない

#### 遷移

```text
ウォーロード撃破 → 第2層解放 → 階層選択で第2層へ移動 → 第2層の仮入口
                                        ↑
                             第1層へ戻ると既存の進行を継続
```

- `layer2Unlocked === false` の間は第2層へ移動できない
- 階層を移動すると、その階層の入口ロケーションへ移る
- 階層移動で第1層の踏破率・ボス撃破・クエスト完了・探索深度などの進行は初期化しない

#### UI

Issue #61で整理した上部領域を「階層選択 ／ その階層のロケーション選択」へ最小拡張した。未解放の階層はロケーションと同じくdisabled＋🔒＋解放条件で示し、現在の階層は「現在」と示す。ヘッダーの階層表示は `state.layer` に追従する。

第2層の仮入口は、コンテンツ未実装であることと第1層へ戻れることだけを表示するplaceholder画面で、現在地の行動（探索・宿屋・鍛冶屋等）を持たない。ロケーション名「第2層 仮入口」もPrototype用の仮称である。

#### このIssueで判断しないこと

正式な階層選択UI（タブ／プルダウン等）、未解放階層の表示方法、正式な多層state構造、`entryLocation` 相当の正式採用、第2層のコンテンツ着手可否は、Human Verificationの結果を見て判断する。

### 15.16 属性構成比による耐性重み付け（Issue #129）

**確定度：Prototype仮採用（検証用）**

Issue #67で導入した耐性計算は、攻撃に含まれる属性の耐性を単純加算していた。Issue #125で武器ごとの通常攻撃属性配分を接続したことで、この式では**属性配分が耐性計算上の重みとして機能していない**ことが明確になったため、耐性側だけを属性構成比で重み付けする候補式へ変更した。

以下はすべて **PROTOTYPE ASSUMPTION** であり、正式な耐性式・弱点・耐性上限は未決である。

#### 変更内容

```text
属性倍率合計 = Σ 属性倍率[i]              ← 行動威力として維持する
属性構成比[i] = 属性倍率[i] / 属性倍率合計
対応耐性 = Σ (属性構成比[i] × 防御側の同属性耐性)

基礎ダメージ = max(0, 物理攻撃力 × 属性倍率合計 - 物理防御力 × (1 + 対応耐性))
```

- 属性倍率合計は行動威力として維持し、耐性側だけを構成比へ正規化する。`斬1.42` の耐性を `0.50 × 1.42` のように増幅しない
- 単一属性の攻撃は構成比100%となり、Issue #67の挙動と一致する
- 属性倍率合計が0以下の攻撃（属性未設定・回復行動等）は対応耐性を0として扱い、0除算しない
- 物理・魔法で同じ処理を共有する。魔法を使う行動は引き続き未実装である
- 通常攻撃は武器の属性配分、SkillはSkill自身の属性配分という Issue #125 の責務は変更していない。どちらも同じ耐性重み付け処理へ渡す
- ダメージ経路は `baseDamage` の1本のままで、二重化していない

| 攻撃 | 敵の斬耐性0.50に対する対応耐性（変更前 → 変更後） |
|---|---|
| 短剣の通常攻撃 `斬1.00` | 0.50 → 0.50（変化なし） |
| 強打 `斬1.42` | 0.50 → 0.50（変化なし） |
| ブロンズソードの通常攻撃 `斬0.60 / 突0.30 / 打0.10` | 0.50 → 0.30 |

#### 既存戦闘への影響

現行Prototypeで0以外の耐性を持つ敵は**洞窟スライム（斬0.50）だけ**であり、強敵・ゴブリン・ウォーロードを含む他の敵はすべて耐性0である。耐性0の敵に対しては変更前後で計算結果が一致するため、影響を受けるのは洞窟スライムに複数属性の攻撃を当てた場合に限られる。

比較は `scripts/compare_resistance_formula.js` で再現できる。同一条件に対して単純加算式と構成比重み付け式の両方をスクリプト内で計算し、対応耐性・基礎ダメージ・最終ダメージを並べて出力する。式変更の影響を隠すための敵能力・武器性能の調整は行っていない。

#### このIssueで判断しないこと

正式な耐性式、弱点（負の耐性）の扱い、耐性の上限／下限、複数属性攻撃が単一属性より有利になりすぎないか、斬／突／打の正式配分、敵耐性値の再調整は、Human Verificationの結果を見て判断する。

### 15.17 装備パラメータ補正と基礎／実効ステータス（Issue #131）

**確定度：Prototype仮採用（検証用）**

Issue #123で整理した装備構造のうち、**装備パラメータ補正 → 実効ステータス → 通常戦闘**と、**Ability条件 → 基礎ステータスのみ参照**の2経路を分離できるかを縦切りで検証した。サブ装備・装飾品・OP・最大HP / MP補正・一時バフへは広げていない。

以下はすべて **PROTOTYPE ASSUMPTION** であり、正式な装備補正値・Ability条件は未決である。

#### 基礎ステータスと実効ステータス

`state.stats` は **基礎パラメータ**のまま維持し、装備変更で直接書き換えない。実効値は毎回導出する。

```text
装備補正[stat] = 現在装備中の武器補正 + 現在装備中の防具補正
実効ステータス[stat] = 基礎ステータス[stat] + 装備補正[stat]
```

- 保存されるのは基礎値だけで、装備変更・セーブ・ロードを繰り返しても補正が二重加算されない
- 集計対象は `STR / VIT / DEX / AGI / INT / MND` の6基本パラメータのみ。最大HP / 最大MP等の派生値補正は未実装
- 集計するスロットは現在実装済みの武器・防具だけで、サブ装備・装飾品スロットは追加していない
- 装備パラメータ補正は `parameterModifiers` として保持し、固定OP／可変OPとは別フィールドにする

#### 通常戦闘は実効ステータスを使用する

戦闘Unit生成時に実効ステータスを渡すため、STR（物理攻撃力）、VIT（物理防御力）、DEX / AGI（ダメージ補正・会心）といった既存処理へ装備補正が自然に反映される。INT / MNDも実効値として導出するが、魔法戦闘は引き続き未実装である。

#### 装備強化はパラメータ補正を増幅しない

装備強化（15.12）は基礎性能（武器ATK / 防具DEF）だけへ作用する。マジックソードを `+10` まで強化してもDEX補正は `+2` のままである。

#### 検証用に追加した装備

| 装備 | 物攻 | 通常攻撃属性 斬/突/打 | 装備パラメータ補正 | 価格 |
|---|---:|---|---|---:|
| マジックソード | 25 | 0.60 / - / 0.40 | DEX+2 | 2200 |

Issue #123のPrototype投入用仮データ候補から、装備パラメータ補正の確認用として1本だけ追加した。レアリティ、工房相性ベクトル、鍛造素材、固定OP「通常攻撃時HP回復」、可変OP、サブ適正は実装していない。物攻25・DEX+2・価格2200・属性比率はすべて仮値であり、正式バランスではない。

スターター装備（訓練用の短剣・旅人の服）にはパラメータ補正を付けていないため、既存シミュレーションの基準条件は変わらない。

#### Ability条件は基礎ステータスだけを参照する

アビリティ定義へ基礎パラメータ条件を持たせ、判定では実効値ではなく `state.stats` の基礎値だけを使う。装備補正を外してから判定する逆算方式ではなく、基礎値と実効値を最初から別経路で持つ。

```text
基礎DEX 7 ＋ マジックソード DEX+2 ＝ 実効DEX 9
斬撃術の条件：基礎DEX 8以上
→ 条件未達（Ability Lvを上げられず、APも消費しない）
```

斬撃術の `基礎DEX 8以上` は**基礎値／実効値の分離を確認するためのPrototype仮値**であり、正式な斬撃術の習得条件ではない。初期DEXが8のため、通常の初期プレイでは従来どおりLvを上げられる。AP消費、Ability Lv、最大Lv、閾値到達時のSkill自動習得、戦術設定への追加といった既存ルールは変更していない。

`基礎DEX 7` の境界ケースは通常プレイでは作れないため、自動テストで確認しており、そのためのデバッグUIは追加していない。

#### UI

- ステータス表示：基礎値と装備補正を区別して `8 (+2)` のように表示する。補正0のステータスへ `(+0)` は表示しない
- アビリティ表示：`条件：基礎DEX 8以上（現在の基礎値 DEX 8）` を表示し、未達時は色を変えて `― 未達` を添える。基礎値だけで判定することを注記へ明記した
- よろず屋の装備一覧へはパラメータ補正を表示していない。正式なステータス画面／装備詳細画面は本Issueで設計していない

#### このIssueで判断しないこと

正式な装備補正値、最大HP / MP等の派生値補正、一時バフを含む最終的な実効値集計順、サブ装備・装飾品を含む集計方式、Abilityごとの正式な基礎パラメータ条件、装備補正とOP補正の将来的な合成順は、Human Verificationの結果を見て判断する。

### 15.19 検証用連続探索と探索分布サマリー（Issue #137）

**確定度：Prototype仮採用（検証支援UI）**

Issue #138で入れた探索一次抽選と2段階ドロップの分布を、数回の手動探索ではなく実測で確認するための**検証支援UI**である。ゲーム内容の追加ではなく、正式ゲームUIとして残すかは決めていない。

以下はすべて **PROTOTYPE ASSUMPTION** である。

#### 通常探索UIとの責務分離

通常プレイの投入スタミナUI（`⚡10 / 20 / 30 / 50`）は変更していない。投入スタミナ量自体もPrototypeの検証対象のため、このUIを回数指定へ置き換えていない。

検証用連続探索は探索実行領域の下へ別ブロックとして置き、破線で区切ったうえで「Prototype検証用操作である」「通常プレイの投入スタミナ選択とは別物である」ことを明示している。

#### 連続探索回数

- 範囲は `1〜100`、刻みは1（Prototype仮値）
- スライダーと数値入力を常に同期する
- 0以下は1へ、101以上は100へ、小数は四捨五入して整数へ丸める
- 空欄・非数値は直前の有効値へ戻す
- 指定回数は同一ランタイム中だけ保持し、探索実行後・再描画後も維持する
- localStorageへ保存せず、プレイヤーのセーブデータへ混在させない。ブラウザを再読み込みすると既定値（50回）へ戻る

ここでいう1回は探索ボタン1回ではなく、**10スタミナごとの探索処理1単位**（＝一次抽選1回）である。`40回` を指定すると ⚡400 を消費する。

#### 連続実行

専用の簡略乱数や専用の報酬処理を作らず、**通常と同じ探索処理**を指定回数ぶん実行する。HP0・満腹度不足などの既存の中断条件も通常探索と同じで、「必ず指定回数を成功させる」専用シミュレータにはしていない。

そのため指定回数と実処理回数は別々に保持し、中断した場合は実処理回数が指定回数を下回る。

```text
指定回数：100
実処理回数：5
中断：あり（満腹度不足）
```

#### 探索分布サマリー

既存の `state.lastResult.summary` を壊さず拡張し、検証用連続探索を実行したときだけ分布を集計して探索結果パネルへ表示する。**通常の投入スタミナ探索では従来どおりの表示のままで、分布サマリーは出さない。**

| 表示項目 | 内容 |
|---|---|
| 実行 | 指定回数 ／ 実処理回数 ／ 中断有無と理由 |
| 一次結果 | アイテムドロップ ／ モンスター遭遇 ／ イベント発生 ／ 探索失敗 ／ 探索進行 の件数 |
| 取得ランク | Rare ／ Uncommon ／ Common の件数 |
| 取得アイテム | 素材ごとの合計取得数（0件のときは「取得なし」と表示する） |

集計は詳細ログの文字列解析ではなく、Issue #138で結果データへ持たせた `primaryCategory` / `dropRank` / `dropItem` / `dropAmount` から行う。中断理由は既存の中断フラグから導出した `interruptReason`（`hp` / `satiety` / なし）で保持する。

既存の探索ログ・戦闘詳細ログは維持しており、ログ件数上限（`logLimit = 60`）も変更していない。100回連続探索時に100回分すべての詳細ログを保持することは目的にしていない。期待値・偏差・グラフ・長期統計保存・CSV出力は対象外である。

#### このIssueで判断しないこと

この検証用連続探索UIを正式ゲームUIとして残すか、回数上限100の妥当性、既定値50の妥当性、分布サマリーの表示項目と粒度、ログ折りたたみ・フィルタ・上限拡大の要否は、Human Verificationの結果を見て判断する。
