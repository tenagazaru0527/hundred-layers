# PROTOTYPE

> Status: Draft v0.1  
> 対象: 2026-08-16時点のPrototype（#35 / PR #36 まで反映）
> この文書は、`GAME_CONCEPT.md` / `GAME_DESIGN.md` で整理したゲーム全体の構想のうち、最初に実際に動かして検証する範囲を定義する。  
> 現時点では、ゲーム全体のMVPではなく **「探索ループ・プロトタイプ」** として扱う。

## 1. プロトタイプの目的

最初から100層、オンライン協力、レイド、職業、生産などを実装するのではなく、まず一人で遊べる最小構成を作る。

このプロトタイプで確認したい中心的な問いは、

> **「スタミナをいくつ使うか決めて探索に出し、ゲーム側で処理された結果を確認し、次の行動を決める」というサイクルに、ゲームとしての面白さがあるか。**

である。

ゲーム全体ではボス攻略やプレイヤー間の相談・編成が重要な体験になるが、このプロトタイプではそこまでを一度に検証しない。

まず、最小単位となる探索部分が成立するかを確認する。

## 3. 現在成立している最小構成

**確定度：Prototype実装済み／各数値は仮値**

```text
育成・戦術を決める
↓
始まりの洞窟へ移動
↓
投入スタミナを決める
↓
探索イベント
├ 深度進行（通常進行 / 近道発見 / 隠し通路）
├ 通常敵遭遇 / 強敵遭遇
├ アイテム発見 / 宝箱
├ トラップ / 回復地点
└ 進行なし
↓
戦闘・トラップでHP消耗、回復地点でHP回復
↓
EXP / 素材 / アイテム / 探索深度を得る
↓
同じ探索成果が世界共通進捗へ加算される（ローカルモック）
↓
続行 / 帰還を判断
↓
街へ帰還
├ 宿屋でHP回復
├ 成長ポイント割り振り
└ モンスター素材・古い硬貨を換金
↓
Gold獲得
↓
ショップで装備購入・装備変更
```

## 4. プレイヤーが行うこと

1. ヘッダーで現在階層、現在地、踏破率、スタミナを確認し、左カラムでHPとEXPを確認する
2. 育成・戦術を決める
3. 街から始まりの洞窟へ移動する
4. 探索に使用するスタミナ量を決める
5. 連続処理された探索イベントと戦闘結果を確認する
6. HPと探索深度を見て、続行か帰還か判断する
7. 街で宿屋、成長ポイント割り振り、素材換金を行う
8. 得たGoldを保持して再探索する

進行中クエストは左カラムのサブ情報として扱い、判断を止めずに必要なときへ確認する（`GAME_DESIGN.md`「25. UI・情報表示の優先順位」）。確認順は次の意味になる。

```text
現在地 / 踏破率 / HP / スタミナを確認
↓
行動を決める
↓
進行中クエストは必要に応じて確認
```

重要なのは、**探索前に決める → 結果を見る → 街で準備する → 次を決める**という流れである。

## 5. 探索イベント

### 5.1 現在の実装

探索開始後は、投入スタミナ10につき1回の探索イベントを連続処理する。

| イベント | 深度 | 確率 |
|---|---:|---:|
| 通常進行 | +4 | 20% |
| 近道発見 | +8 | 10% |
| 隠し通路 | +12 | 5% |
| 通常敵遭遇・勝利 | +8 | 35%枠内 |
| 通常敵遭遇・敗北 | +0 | 35%枠内 |
| 強敵遭遇・勝利 | +8 | 5%枠内 |
| 強敵遭遇・敗北 | +0 | 5%枠内 |
| アイテム発見 | +4 | 8% |
| 宝箱 | +4 | 4% |
| トラップ | +0 | 4% |
| 回復地点 | +0 | 3% |
| 進行なし | +0 | 6% |

確率の合計は100%、戦闘系イベント（通常敵 + 強敵）の合計は40%である。トラップはHPを10減少させ、HPは0未満にならない。回復地点はHPを20回復し、最大HPを超えない。宝箱は「古い硬貨 ×2 / 鉄鉱石 ×2 / 薬草 ×2」から1種類を取得する。いずれもGoldを直接付与しない。

HP0到達時は残イベントを処理せず中断し、投入済みスタミナは返却しない。確率、深度値、トラップ / 回復地点のHP量、宝箱の内容はすべて **PROTOTYPE ASSUMPTION** である。

初期案の `+1 / +2 / +3` 等はHuman Verification前の1回限りのテンポ補正で4倍された。PR #36の実測では、スタミナ100（探索イベント最大10回）あたりの平均深度進行は約28.0、HP0による中断割合は約87.8%であり、#35実装前の約27.7 / 約91.2%と同水準である。本格バランスが確定したとは扱わない。

## 6. スタミナ

現在Prototypeのスタミナは最大値を持たず、世界開始日時からの経過時間で蓄積する（Issue #58）。現在値は保存せず、次式で算出する。

```text
現在スタミナ = 初期スタミナ + max(0, floor((現在時刻 - WORLD_OPEN_AT) / 1000)) × 回復速度 - 累計使用スタミナ
```

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. `WORLD_OPEN_AT` はPrototypeの固定設定値であり、プレイヤーの初回アクセス時に決めない
2. 初期スタミナは0、回復速度は現実時間1秒につき1とする
3. 最大値を設けず、100でも100,000でも上限なく蓄積する。オフライン中も経過時間として蓄積される
4. 探索イベント1回につき10を消費し、10 / 20 / 30 / 50から投入量を選べる
5. 通常操作で負数にならないよう、算出結果は0未満を返さない
6. プレイヤー状態は現在値ではなく累計使用スタミナ `staminaSpent` を保持する
7. `GAME_TIME_SCALE` とスタミナ回復速度は連動しない

同じワールド・同じ時刻・同じ累計使用量であれば、参加日時にかかわらず同じスタミナになる。UIでは `⚡` と数値のみを表示し、最大値に対する割合バーは持たない。

旧仕様（最大100・1分1回復・現在値保存）からの移行では、保存値 `stamina` に `lastStaminaUpdate` からの未反映回復分（1分1回復、旧仕様の最大100で頭打ち）を加えた「旧仕様上の現在スタミナ」を求め、その値を維持するよう累計使用量を逆算する。移行が発生した場合はプレイヤーの操作を待たずに新形式でlocalStorageへ書き戻し、再読込時に再移行しないようにする。旧 `stamina` / `lastStaminaUpdate` / `worldStart` は読み込み時に破棄する。正式な最大値の有無、初期値、回復速度、投入上限は未決である。

## 7. ダンジョン深度・踏破率

始まりの洞窟はダンジョン深度100を持つ。プレイヤー状態に `explorationDepth` を保持し、次式で踏破率を算出する。

```text
踏破率(%) = explorationDepth / dungeonDepth × 100
```

旧保存データの `progress` は探索深度へ移行し、`progress` と `explorationDepth` を同義の状態として二重保持しない。深度値は **PROTOTYPE ASSUMPTION** である。

`explorationDepth` から算出する個人踏破率は個人の状態であり、Issue #56以降は通常画面へ表示しない。UIが「踏破率」として表示するのは共有進行値（15.3）であり、ボス討伐メニューの解放条件もこの共有進行値100%である。内部の `explorationDepth` は保持と加算を継続している。

正式設計では、ダンジョン探索進行をロケーション自身に紐づく全プレイヤー共有状態とし、UIでは「踏破率」のみ表示する。個人 `explorationDepth`／個人踏破率は本番モデルに持たない方向であり、本節は現行Prototypeの移行前状態を記録している。本IssueではコードとlocalStorage構造を変更しない。

## 8. 戦闘・育成・帰還・報酬

### 8.1 戦闘と育成

ターン制オートバトル、通常攻撃 / 強打の戦術設定、物理ダメージ、DEX / AGI補正、会心を実装済みである。STR / VIT / DEX / AGIへポイントを割り振ることができ、INT / MNDの戦闘効果は未実装である。

敵は次の4種を同一の戦闘エンジンで共通処理し、敵ごとに6基礎ステータス、行動、EXPを持つ。Lv / EXP、余剰EXP持越し、複数LvUP、旧名称のパラメータポイント／スキルポイントも保持する。

正式設計では、パラメータポイントをステータスポイント（SP）、スキルポイントをアビリティポイント（AP）へ整理し、「基本パラメータ → アビリティ → スキル」の育成構造を採用している。ただし、本IssueではPrototype実装を変更しないため、現状との差分は次の通りである。

- 保存データと実装上の変数名は旧 `parameterPoints` / `skillPoints` のままである。表示名のみIssue #56でSP（ステータスポイント）／AP（アビリティポイント）へ統一した
- SP相当の割り振りはSTR / VIT / DEX / AGIのみ実装済みで、INT / MNDは未実装である
- APの消費、アビリティ解放／Lv上昇、アビリティLvによるスキル自動習得は未実装である
- アクティブ／リアクション／トリガー／パッシブのスキル分類は未実装である
- 現行の「強打」はPrototype戦闘用の仮行動であり、正式スキルとして確定していない

| 敵 | 枠 | Prototype上の役割 |
|---|---|---|
| ゴブリン | 通常敵 | 比較的安全な基準敵 |
| 洞窟コウモリ | 通常敵 | ゴブリンより危険 |
| 洞窟スライム | 通常敵 | 低火力・高耐久寄り |
| 洞窟オーク | 強敵 | 「強敵遭遇」イベント専用。高リスク高成果 |

通常敵は「通常敵遭遇」から、洞窟オークは「強敵遭遇」から出現し、遭遇プールを分けている。各敵のHP、能力値、行動威力、EXPはいずれも **PROTOTYPE ASSUMPTION** であり、正式仕様として扱わない。洞窟スライム / 洞窟オークはPR #36で追加した仮値である。属性・耐性・状態異常・特殊技・複数体戦闘は追加していない。

PR #20 / #22の実測では、ゴブリン / 洞窟コウモリについて、敵によってDEX / AGIの効き方が異なる一方、STR / VITは両敵に対して依然として強く、敵ごとに最適育成が完全に分かれる段階には至っていない。正式バランスの確定ではなく、差分型ダメージ式の成長曲線は今後の課題である。

洞窟オークのみ、通常敵AIとして最小Utility AIを適用している（Issue #48）。共通評価関数 `utilityScore` が敵ごとの `ai` 設定（各行動の `baseScore` / `targetLowHpBonus` / `selfLowHpBonus` と `thresholds.targetLow` / `selfLow`）を参照し、現戦況（自HP率とプレイヤーHP率）からScoreを計算して最大値の行動を選ぶ。同点時は行動リストの先頭側を優先する。洞窟オークの性格は「相手を仕留めに行く／追い詰められた時に強行動を選ぶ」を1案に固定し、通常時は殴打、プレイヤーHPが低い時または自HPが低い時に兜割りへ切り替わる。Score値・閾値はすべて **PROTOTYPE ASSUMPTION** である。ゴブリン / 洞窟コウモリ / 洞窟スライムは比較のため従来の固定確率行動を維持している。AI設定は現段階では単一HTMLの `CONFIG` 内に置き、外部JSON化は行っていない。

### 8.2 HP持越しと宿屋

`currentHp`を保持し、戦闘終了HPを次戦へ持ち越す。勝利後も自動全回復しない。HP0では探索不可だが街へ帰還でき、街へ移動しただけでは回復しない。街の無料宿屋で最大HPまで回復する。

無料宿屋、HP0、死亡・ロストなしの扱いは **PROTOTYPE ASSUMPTION** である。

### 8.3 固有素材とGold

戦闘勝利時は敵固有素材を1個必ず獲得する。戦闘勝利によるGold直接付与は停止済みである。

| 入手元 | 素材 | 換金額 |
|---|---|---:|
| ゴブリン | ゴブリンの牙 | 4 Gold |
| 洞窟コウモリ | コウモリの翼膜 | 5 Gold |
| 洞窟スライム | スライムの粘液 | 3 Gold |
| 洞窟オーク | オークの角 | 8 Gold |
| 探索イベント（アイテム発見 / 宝箱 / 戦闘報酬） | 古い硬貨 | 2 Gold |

街で素材を1個ずつ換金する。薬草と鉄鉱石は引き続き探索・戦闘報酬として存在するが、換金対象ではない。宝箱もアイテムのみを付与し、Goldを直接付与しない。入手率100%、入手量、換金額は **PROTOTYPE ASSUMPTION** である。

```text
探索 / 戦闘 → 成果（素材・アイテム） → 街 → 換金 → Gold
```

## 11. このプロトタイプで検証したいこと

### 11.1 基本ループが成立するか

```text
判断
↓
探索開始
↓
結果確認
↓
次の判断
```

という繰り返しを、プレイヤーが続けたいと感じるか。

### 11.2 自動探索の結果を見ることに面白さがあるか

自分で直接操作しない探索でも、

> 「何が起きたのか確認したい」

と思える結果になっているか。

### 11.3 スタミナ投入量が意思決定になるか

現在の最も重要な未解決点。

もし、

> 多く投入するほど単純に得

であれば、常に投入可能な最大値を使うのが正解となり、プレイヤーが考える余地がない。

そのため、

> **「なぜスタミナを全部投入しないのか」**

という問いに答えられるかを確認する必要がある。

現時点では解決策を決めない。

候補として探索場所、探索方針、リスク等の要素を追加する可能性はあるが、この文書では仕様化しない。

### 11.4 探索深度・踏破率が次の探索動機になるか

探索深度・踏破率が、

> 「あと少し探索したい」

という継続動機になるかを確認する。

単に数字が100%へ増えるだけでは単調になる可能性があるため、実際に遊んで判断する。

## 12. プロトタイプの成功判定

現時点では、定量的な成功基準はまだ決めない。

まず以下を人間が実際に触って確認する。

- 結果を見るまでの流れが苦痛ではない
- 探索結果を確認したあと、もう一度探索したくなる
- 投入スタミナ量について考える意味がある
- 探索深度・踏破率の上昇が進行感として機能する
- 自動処理でも「自分の判断の結果」と感じられる
- 単純な作業の繰り返しになっていない

これらが成立しない場合、オンライン機能や100層構造へ進む前に探索ループを再設計する。

## 15. 現行Prototypeで置いている最小仮定

### 15.1 ショップ・装備

最小ショップと装備変更はPR #30で実装済みであり、以下を **PROTOTYPE ASSUMPTION** として置いている。

1. 「訓練用の短剣（ATK 11）」「旅人の服（DEF 11）」を初期所持・初期装備とする
2. 旧保存データではスターター装備を安全に補完する
3. 購入候補は「鉄の短剣（ATK 13、15 Gold）」「革の鎧（DEF 13、15 Gold）」を各1種類とする
4. 街でのみ購入でき、Gold不足・購入済みの場合は購入できない
5. 重複所持はせず、購入だけでは自動装備しない
6. 所有装備から武器・防具を各1つ装備し、スターター装備へ戻せる
7. 所有・装備状態をlocalStorageへ保存し、不正IDはスターター装備へフォールバックする

```text
攻撃値 = STR + 現在武器ATK
防御値 = VIT + 現在防具DEF
```

価格・性能は反復調整しない。本格装備・経済仕様は確定していない。

### 15.2 ゲーム内日時

ゲーム内日時はPR #32で実装し、Issue #58で表示粒度と起点を更新した。ヘッダーに表示専用として表示する。以下は **PROTOTYPE ASSUMPTION** である。

1. 現実時間の100倍で進行する（`GAME_TIME_SCALE = 100`）
2. 1年365日、1ヶ月28日、13ヶ月の独自暦と7曜日を保持し、年末の1日は「竜触の刻」として扱う
3. 起点はプレイヤーごとの `worldStart` ではなく、ワールド共通の設定値 `WORLD_OPEN_AT` とする。旧セーブの `worldStart` は読み込み時に破棄する
4. 通常日の表示は月名・第何週か（1〜4）・曜日のみとする。週番号は1か月28日を7日ずつ区切って算出する
5. 年、月内の具体的な日付、時刻は内部計算として保持するが、通常画面へ表示しない
6. 特別日は月・週・曜日の代わりに「竜触の刻」だけを表示する
7. 現時点では表示のみで、探索、戦闘、ショップ等へのゲーム効果を持たない。スタミナ回復速度とも連動しない

暦の算出は現在時刻を注入できる関数 `calendarParts(now)` に寄せ、固定時刻での自動確認を可能にしている。「竜触の刻が内部的な曜日周期を1日進めるか」は既存の未決事項のままである。

オンライン実装時の時間進行方式、サーバー時刻との同期、時間帯によるゲーム効果は未決であり、ここでは正式化しない。

### 15.3 世界共通進捗のローカルモック

単一プレイヤーの探索成果を世界全体の探索成果として扱うローカルモックは、Issue #44で実装済みである。

```text
世界共通クエストを確認
↓
探索する
↓
ローカル上の世界共通進捗が増える
↓
100%到達
↓
ボスメニューが1回だけ解放
↓
100%済みロケーションにも引き続き入り、通常探索できる
```

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. `worldState`（世界共通進捗、クエストStep、階層ボス解放状態）を、プレイヤー状態とは別のlocalStorageキーへ保存する
2. 個人の `explorationDepth`／個人踏破率とは別概念として保持し、同一値として扱わない
3. 探索イベントで得た深度進行量を、そのまま世界共通進捗への仮加算量として利用する
4. 世界共通進捗は100%を上限とし、100%を超えて保持しない
5. 世界共通進捗100%で階層ボスを解放し、解放処理は1回だけ成立する
6. 100%到達後も通常探索・戦闘・素材収集を継続でき、世界共通進捗は100%から増加しない
7. クエストタイトルと本文は固定データで、100%到達後にボス発見済みの文へ切り替える。ゲーム実行中に生成AI APIを呼び出さない

Issue #56以降、この共有進行値はUI上「踏破率」として表示する（15.4）。内部の状態名 `worldState.progress`、加算方法、100%到達処理は変更していない。

単一プレイヤーの探索を世界全体の成果とみなす点、および加算量そのものが仮であり、本番の世界進捗加算方式ではない。本番のオンライン共有DB、バックエンド、複数プレイヤーの同時更新・排他制御は実装していない。必要探索量と個人貢献も確定していない。

`worldState.progress` は単一値であり、複数ダンジョンの共有踏破率をロケーション単位で保持する正式モデルには不足する。将来の状態モデル再構築時に、個人 `explorationDepth` とあわせて移行対象とする。クエストStepとロケーション踏破率は別概念として保持できる必要がある。

### 15.4 通常画面のUI構造

Issue #56で、`GAME_DESIGN.md`「25. UI・情報表示の優先順位」の領域分担を現行Prototypeへ実装した。共同開発者の `prototype_updated.html` はレイアウト／情報階層の参照資料として使用し、コードの基準は最新 `main` の `prototype.html` とした。

```text
ヘッダー：ゲーム内暦（月 / 第何週 / 曜日）/ スタミナ（⚡と数値）/ 現在階層 / 現在地 / 踏破率（ダンジョンのみ）
ヘッダー直下：ロケーション移動
左カラム：進行中クエスト / 冒険者の基本情報 / ステータス・スキル/アビリティ・所持品メニュー
右カラム：現在選択中の操作と直後の結果（探索・町・ステータス・スキル/アビリティ・所持品）
フッター：システムログ（探索履歴を統合）/ デバッグ操作 / Title・Version
```

以下を **PROTOTYPE ASSUMPTION** として置いている。

1. ヘッダーの階層表示は `現在階層` と呼び、プレイヤーが現在いる階層を指す。世界全体の最新攻略階層ではない
2. 世界全体の最新攻略階層に対応する状態は保持しておらず、Prototypeでは表示しない
3. ダンジョン滞在時のみ、共有進行値 `worldState.progress` を「踏破率」として表示する。街では表示しない
4. 右カラムの表示対象は `activeView`（`main` / `status` / `skills` / `items`）で切り替える。`activeView` は表示状態のみでlocalStorageへ保存せず、画面履歴やルーティングは持たない
5. SPはステータスポイント、APはアビリティポイントとして表示し、Lv付近で未使用分を確認できる
6. スタミナは最大値を持たないため、ヘッダーでは `⚡` と現在値のみを表示し、割合バーを持たない。探索の投入量ボタンも `⚡10` 形式で表記する（Issue #58）

### 15.5 UI構造と状態モデルの差分

Issue #56はUI移植であり、状態モデルの移行は行っていない。現時点で残る差分は次の通りである。

- ロケーション別の共有踏破率は未実装である。表示上の「踏破率」は単一値 `worldState.progress` を参照しており、ロケーション単位の共有状態ではない
- 個人 `explorationDepth` は保持と加算を継続しており、削除していない。ただし通常画面の主要情報としては表示せず、デバッグ操作でのみ内部値として確認できる
- 内部変数名は旧 `parameterPoints` / `skillPoints` のままであり、表示名のみSP / APへ統一している。localStorageスキーマは変更していない
- Ability / Skillは未実装である。スキル・アビリティ画面は未使用APの確認のみで、アビリティLv割り振りとスキル習得処理を持たない
- アルンの森、ゴブリンの巣穴、ロケーションunlock、クエストStep遷移、第2層unlockは実装していない。Issue #54で整理した第1層Prototype進行モデル（15.7）は文書化済みで、コードへの実装は後続Issueとする

参照HTML内のMP、UI確認用スタミナ値、旧ポイント名称、旧クエストモデル、Utility AI導入前の戦闘処理、参照HTML側のVersion番号は移植していない。

### 15.6 今後の進め方

100%後のねらいうち探索は有力案だが、この最小モックの検証には含めず、その後の別Issue候補とする。まずは「個人の探索が一つの世界を進める」感覚と、100%後もロケーションを利用できる流れをHuman Verificationで確認する。

### 15.7 第1層Prototype進行モデル

**Prototype向け設計／未実装**

Issue #54では、正式な世界進行構造を第1層の具体的なコンテンツへ落とし込み、「探索 → 世界変化 → 次の目標 → ボス → 次階層」という基本サイクルを検証するモデルを次のように整理する。この内容は現行 `prototype.html` へ未実装であり、第1層固有の名称や条件を全階層共通仕様として固定するものではない。

#### ロケーションと開始状態

| 種別 | 名称 | Prototype開始時 |
|---|---|---|
| 街 | はじまりの街 アルマセント | 解放済み |
| ダンジョン | アルンの森 | 解放済み |
| ダンジョン | ゴブリンの巣穴 | 未解放 |

開始時の進行中クエストは「アルンの森を調査せよ」とする。開始時点ではゴブリンの巣穴へ移動できない。未解放ロケーションを非表示、ロック表示、disabled表示のどれにするかは未決のままとする。

#### 基本攻略サイクル

```text
はじまりの街 アルマセント
↓
「アルンの森を調査せよ」進行中
↓
アルンの森を共同探索
↓
アルンの森 踏破率100%
↓
「アルンの森を調査せよ」完了
↓
「ゴブリンを掃討せよ」開始
↓
ゴブリンの巣穴 解放
↓
ゴブリンの巣穴を共同探索
↓
ゴブリンの巣穴 踏破率100%
↓
「ゴブリンを掃討せよ」のStep更新
↓
ゴブリン・ウォーロード 解放
↓
ゴブリン・ウォーロード撃破
↓
「ゴブリンを掃討せよ」完了
↓
第2層への移動解放
```

各遷移は条件成立時に1回だけ発火する。アルンの森とゴブリンの巣穴はそれぞれ独立した共有踏破率を持ち、100%到達後も通常探索を継続できる。

「ゴブリンを掃討せよ」は巣穴探索とボス撃破を別クエストへ分割せず、1つの世界共通クエスト内で次のようにStepを進める。

```text
Step 1：ゴブリンの巣穴を調査する
↓ 巣穴 踏破率100%
Step 2：ゴブリン・ウォーロードを討伐する
↓ ボス撃破
クエスト完了
```

クエスト本文、NPC台詞、詳細な演出文は確定しない。ゴブリン・ウォーロードについても、第1層の世界進行上でアンロック状態と撃破状態を持つことだけをこのモデルで定める。ステータス、スキル、AI、ギミック、戦闘形式、参加人数、開始方法、報酬、再戦可否は未決である。

ボス撃破後は「ゴブリンを掃討せよ」の完了と第2層への移動解放を1回だけ発火する。第2層の街、ダンジョン、クエスト、敵、コンテンツ名、開始状態は本モデルの対象外であり、第2層そのものは実装しない。

#### 状態の責務

第1層の進行を単一の `progress` や `step` へ集約せず、少なくとも次を別状態として扱う。

```text
worldState
├ locations
│  ├ forest
│  │  ├ unlocked
│  │  └ progress
│  └ cave
│     ├ unlocked
│     └ progress
├ quest
│  ├ currentQuest
│  └ step
├ bosses
│  └ goblinWarlord
│     ├ unlocked
│     └ defeated
└ layers
   └ layer2Unlocked
```

これは責務分離を説明する概念例であり、正式なJavaScriptオブジェクト構造や変数名を固定しない。特に、森の踏破率、巣穴の踏破率、クエスト状態／Step、ロケーションアンロック、ボスアンロック、ボス撃破、第2層アンロックを同一状態にしない。

#### 現行Prototypeとの差分

現行Prototypeには、個人 `state.explorationDepth`、単一 `worldState.progress`、旧ロケーション名、旧クエスト文言／単一クエストモデルが残っている。ロケーションごとのアンロック状態はなく、ボス戦はプレースホルダーで、第2層解放も実装していない。

将来のPrototype実装では「始まりの街」「始まりの洞窟」を本節の名称へ置き換え、ロケーション別共有踏破率と各アンロック状態へ移行する。本Issueでは `prototype.html`、localStorage、`worldState`、個人 `explorationDepth` を変更しない。
