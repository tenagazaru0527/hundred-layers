# PROTOTYPE

> Status: Draft v0.1  
> 対象: 2026-08-13〜2026-08-14までの企画議論  
> この文書は、`GAME_CONCEPT.md` / `GAME_DESIGN.md` で整理したゲーム全体の構想のうち、最初に実際に動かして検証する範囲を定義する。  
> 現時点では、ゲーム全体のMVPではなく **「探索ループ・プロトタイプ」** として扱う。

## 1. プロトタイプの目的

最初から100層、オンライン協力、レイド、職業、生産などを実装するのではなく、まず一人で遊べる最小構成を作る。

このプロトタイプで確認したい中心的な問いは、

> **「スタミナをいくつ使うか決めて探索に出し、ゲーム側で処理された結果を確認し、次の行動を決める」というサイクルに、ゲームとしての面白さがあるか。**

である。

ゲーム全体ではボス攻略やプレイヤー間の相談・編成が重要な体験になるが、このプロトタイプではそこまでを一度に検証しない。

まず、最小単位となる探索部分が成立するかを確認する。

---

## 2. このプロトタイプの位置づけ

**確定度：高**

この試作は、ゲーム全体の完成形を縮小したものではない。

検証対象を絞った **探索システムの試作** である。

ゲーム全体の最終構想には、

- 多数のプレイヤー
- 100層攻略
- 階層ボス
- パーティー
- レイド／攻略隊
- 戦闘職
- 生産職
- プレイヤー同士の相談・情報共有

などが含まれる。

しかし、これらは今回の最初の試作には含めない。

## 3. 最小構成

**確定度：高**

最初に動かす範囲は以下。

```text
街 × 1
↓
洞窟へ移動
↓
洞窟 × 1
↓
使用するスタミナ量を決定
↓
探索開始
↓
ゲーム側で探索を自動処理
↓
探索結果を表示
↓
開拓率を更新
↓
次の探索へ
```

洞窟の開拓率が100%になると、**ボス討伐メニューがアンロックされる**案を採用候補とする。

ただし、実際のボス戦まで今回のプロトタイプへ含めるかは未決。

### UI

PrototypeのUIは `GAME_DESIGN.md` の「UIデザイン方針」に従う。

現在のPrototypeでは、

- 基準配色
- 日本語UI
- 単色SVGによる主要メニューアイコン
- 最小ターン制オートバトル
- 戦闘勝利時のアイテム・Gold報酬
- 通常攻撃／強打の戦術設定
- STR / VIT / DEX / AGI / INT / MND の保持・表示
- STRと武器性能の物理攻撃への接続
- VITと防具性能の被物理ダメージへの接続
- Lv / EXP / パラメータポイント / スキルポイントの保持・表示
- 戦闘勝利時のEXP獲得と複数LvUP
- STR / VITへのポイント割り振りと戦闘反映

を適用済み。

## 4. プレイヤーが行うこと

このプロトタイプでプレイヤーが行う中心的な操作は以下。

1. 街から洞窟へ移動する
2. 洞窟の現在状況を確認する
3. 探索に使用するスタミナ量を決める
4. 探索を開始する
5. 自動処理された探索結果を確認する
6. 更新された開拓率や残りスタミナを確認する
7. 次の探索を行うか判断する

重要なのは、探索中をリアルタイムに操作することではなく、

**探索前に決める → 結果を見る → 次を決める**

という流れである。

---

## 5. 探索処理

### 5.1 基本方式

**検討中。ただし現在の中心案**

探索開始後は、ゲーム側で探索内容を自動処理する。

プレイヤーは探索中の移動や戦闘を一つずつ操作しない。

探索結果として、現時点では以下が候補となっている。

- 敵との遭遇
- アイテム獲得
- 開拓率の上昇

### 5.2 ランダム性

**検討中**

同じスタミナ量を投入しても、必ず同じ結果になるとは限らない方向が出ている。

例えば、

- 敵との遭遇が多かった
- 比較的安全に探索できた
- アイテムを獲得した

などによって、同じスタミナ量でも開拓率の伸び方や結果が変わる可能性がある。

ただし、具体的な確率や結果テーブルは未決。

## 6. スタミナ

### 6.1 基本的な役割

**検討中。ただしプロトタイプの中心要素**

探索に使う有限資源としてスタミナを置く。

プレイヤーは、探索開始前に

> **「今回の探索にスタミナを何ポイント使うか」**

を決める。

### 6.2 回復

**検討中**

仮案として、

> **1分につき1ポイント回復**

という案が出ている。

この値はゲームバランス上の確定値ではない。

単純計算では、

- 30日: 43,200ポイント
- 31日: 44,640ポイント

となるため、実際には最大値、投入量、回復上限などを別途設計する必要がある。

### 6.3 未決事項

以下は未決。

- 最大スタミナ
- 初期スタミナ
- 1回の投入上限
- 1回の最低投入量
- 回復上限
- オフライン時の回復
- スタミナが0の場合の扱い
- スタミナと探索時間の関係

## 7. 開拓率

### 7.1 プロトタイプ上の役割

**検討中。ただし重要な進捗指標**

洞窟の攻略進行を示す値として、開拓率を使用する。

探索結果によって開拓率が上昇する。

```text
探索
↓
探索結果
↓
開拓率上昇
↓
100%
↓
ボス討伐メニュー解放
```

### 7.2 この試作での扱い

このプロトタイプは一人用なので、開拓率はまず一人分の進捗として扱う。

オンライン版で、

- 個人進捗
- パーティー進捗
- 世界全体の共有進捗

のどれにするかは、今回の試作では決めない。

### 7.3 未決事項

- 1回の探索でどの程度上昇するか
- 敵との遭遇によってどの程度変化するか
- アイテム獲得と開拓率の関係
- 失敗時に開拓率が上がるか
- 開拓率が具体的に何を意味するか

## 8. 戦闘

### 8.1 プロトタイプでの位置づけ

**最小ターン制オートバトル、戦闘報酬、戦術設定、6基礎ステータス、装備性能、最小育成ループは追加済み。以降の拡張候補は本番仕様と区別する。**

現在のPrototypeでは次のループが成立している。

```text
戦術設定
↓
探索
↓
戦闘
↓
EXP獲得
↓
LvUP
↓
パラメータポイント獲得
↓
STR / VIT割り振り
↓
戦闘能力変化
```

プレイヤー状態はSTR / VIT / DEX / AGI / INT / MNDを保持する。STR / VITのみポイント割り振り可能で、現在の固定行動ダメージへ加える暫定的な戦闘補正式へ接続済みである。DEX / AGI / INT / MNDの効果は未実装である。

Lv / EXP / パラメータポイント / スキルポイントも保持・表示し、戦闘勝利時のEXP獲得、余剰EXP持ち越し、複数LvUP、レベルごとのポイント付与を実装済みである。

具体的な能力値、装備性能、EXP式、ポイント付与量、戦闘式、確率、報酬テーブルはすべて **PROTOTYPE ASSUMPTION** であり、本番仕様ではない。

### 8.2 次の検証対象：基礎ステータスを用いた物理ダメージ計算

**次のPrototype候補。今回は実装しない。**

```text
STR / VIT / DEX / AGI
＋
装備
＋
行動威力
↓
物理ダメージ計算
↓
会心判定
↓
戦闘結果
↓
ポイント配分変更
↓
再戦
```

次の検証では、現在の「固定行動ダメージ＋STR / VIT補正」を、攻撃側と防御側の基礎ステータス・装備性能・行動威力・DEX / AGI補正・会心から求めるPrototype式へ置き換える。

確認したいこと：

- STRを上げた場合に期待どおり攻撃性能が変わるか
- VITを上げた場合に期待どおり耐久性能が変わるか
- DEXを選ぶ理由が生まれるか
- AGIを選ぶ理由が生まれるか
- STR一極・DEX一極等にならないか
- 防御系ステータスへポイントを振る意味があるか
- 通常攻撃／強打の戦術設定と能力値育成が相互に意味を持つか
- 敵能力値によって育成・戦術を変えたくなるか

物理ダメージ式、行動威力倍率、DEX / AGI補正、会心倍率、敵能力値は **PROTOTYPE ASSUMPTION** とする。INT / MND、魔法、MP、Utility AI、独自乱数方式は対象外とする。

### 8.3 現時点で決めないこと

- 本格ショップ
- 詳細な装備システム
- 本格スキルシステム
- Utility AI
- 条件付き戦術設定
- ボス戦
- 複雑なドロップ設計
- 本格的なダメージ計算・バランス調整
- パーティー戦
- 職業別戦闘

これらは、物理ダメージ計算を検証する場合も後回しにする。現在の探索・戦闘・育成ループを損なわない範囲でのみ、最小構成を追加する。

## 11. このプロトタイプで検証したいこと

### 11.1 基本ループが成立するか

```text
判断
↓
探索開始
↓
結果確認
↓
次の判断
```

という繰り返しを、プレイヤーが続けたいと感じるか。

### 11.2 自動探索の結果を見ることに面白さがあるか

自分で直接操作しない探索でも、

> 「何が起きたのか確認したい」

と思える結果になっているか。

### 11.3 スタミナ投入量が意思決定になるか

現在の最も重要な未解決点。

もし、

> 多く投入するほど単純に得

であれば、常に投入可能な最大値を使うのが正解となり、プレイヤーが考える余地がない。

そのため、

> **「なぜスタミナを全部投入しないのか」**

という問いに答えられるかを確認する必要がある。

現時点では解決策を決めない。

候補として探索場所、探索方針、リスク等の要素を追加する可能性はあるが、この文書では仕様化しない。

### 11.4 開拓率が次の探索動機になるか

開拓率が、

> 「あと少し探索したい」

という継続動機になるかを確認する。

単に数字が100%へ増えるだけでは単調になる可能性があるため、実際に遊んで判断する。

## 12. プロトタイプの成功判定

現時点では、定量的な成功基準はまだ決めない。

まず以下を人間が実際に触って確認する。

- 結果を見るまでの流れが苦痛ではない
- 探索結果を確認したあと、もう一度探索したくなる
- 投入スタミナ量について考える意味がある
- 開拓率の上昇が進行感として機能する
- 自動処理でも「自分の判断の結果」と感じられる
- 単純な作業の繰り返しになっていない

これらが成立しない場合、オンライン機能や100層構造へ進む前に探索ループを再設計する。

## 15. 次のPrototypeで置く最小仮定

物理ダメージ計算の検証時は、以下を本番仕様ではなく **PROTOTYPE ASSUMPTION** として置く。

1. 敵もSTR / VIT / DEX / AGI / INT / MNDを保持する
2. 物理攻撃値はSTR＋武器攻撃力、物理防御値はVIT＋防具防御力とする
3. 基礎ダメージは `max(0, 攻撃値 - 防御値)` とし、最低1ダメージを保証しない
4. 行動威力倍率は通常攻撃1.0、強打1.8、ひっかき1.0、振り下ろし1.4とする
5. DEX / AGI補正は `1 + (攻撃側DEX - 防御側AGI) / 100` とする
6. 会心率は `max(0, 攻撃側DEX - 防御側AGI)%`、会心倍率は2倍とする
7. パラメータ割り振りをSTR / VIT / DEX / AGIへ広げ、INT / MNDは対象外とする
8. 負ダメージによって相手HPが回復しない安全処理を行う

倍率下限、会心率上限、端数処理、補正係数、行動威力の正式方式、敵装備相当値、物理と魔法の補正共通化はこの検証で確定しない。
