# 開発プロセス方針

この文書は、Hundred LayersにおけるAI活用、検証、Human Verification（HV）、および開発プロセス改善の基本方針を記録する。

この文書はゲーム仕様のSSOTではない。ゲーム仕様、Prototypeの仕様、確定度は、`docs/DOC_MAP.md` が示す各SSOTを正とする。Agentの具体的な実行ルールは `AGENTS.md`、個別作業のScope / Out of Scope / Acceptance Criteriaは各Issue、Issue / PRの運用ルールは `CONTRIBUTING.md` と各テンプレートを正とする。

## 1. 目的

AI活用の目的は、コンテンツや文章の大量生成ではなく、人間が設計判断、Human Verification、共同開発者間の合意に使える時間を増やすことである。

AI導入によって生成量だけでなく人間の確認量まで増える場合、それは改善とはみなさない。目指すのは、次の人間判断に必要な調査、整理、計算、確認を、可能な範囲でAIまたはスクリプトへ移すことである。

## 2. 人間とAIの責務分担

責務は職種や作業領域ではなく、出力を機械的に判定できるかを基準に分ける。

### AI・スクリプトへ移しやすいもの

- スキーマ適合、必須フィールド、ID・参照整合
- 既存仕様との矛盾候補、参照先の存在、重複、異常値、偏りの検出
- 確率・数値範囲、期待値、分散、境界条件、入力感度の確認
- シミュレーション、極端ケース、支配的戦略候補の確認
- 自動テスト、save / load / migrationの整合確認
- 実装と文書の差分候補の検出
- Human Verification用の状態準備、確認項目・結果の整理

### 人間に残すもの

- 次に何を検証するか
- 何を面白さとするか
- 何を正式仕様へ昇格するか
- Human Verificationでどう感じたか
- 数値の許容帯と、意図的な例外
- 世界観、層テーマ、主要固有名
- 重要なアーキテクチャ・運用判断
- 共同開発者間の合意

AIや自動検証の結果は判断材料であり、人間の判断そのものではない。特に自動検証のPASSを、面白さ、理解しやすさ、体感、またはHV完了の根拠にしない。

## 3. 基本的な検証順序

Issueの仮説と変更範囲に応じて、必要な検証だけを選ぶ。全Issueで全工程を必須にはしない。

原則となる順序は次のとおりである。

```text
自動テスト
→ 数理検証・シミュレーション
→ 必要な場合は敵対的プレイテスト
→ Human Verification
→ 人間判断
```

Human VerificationはAI評価やシミュレーションで代替しない。自動検証とHVの結果は分けて記録し、HVが残る場合は完了扱いにせず、`REVIEW_REQUIRED`として人間へ引き渡す。

## 4. 設計・開発監督

万能な監督AIや、最初から全工程を集計する汎用基盤は新規構築しない。既存のGitHub、`docs/DOC_MAP.md`、`AGENTS.md`、Issue / PR運用へ、必要なものを小さく追加していく。

将来的には、PR単位で次を確認できる状態を目指す。

- 関連するDOC_MAPテーマと確認したSSOT
- 古くなる可能性がある設計記述
- 関連する`OPEN_QUESTIONS.md`とDecisionの再検討条件
- 必要なAutomated Test、Simulation、Adversarial Playtest
- Human Verificationの要否と、Docs Syncの要否

検証状態は、将来必要になった段階で `DONE / PENDING / N/A` など機械的に扱える形式へ寄せる。ただし、この文書の追加時点では、その仕組み自体は実装しない。

## 5. 数値設計の事前反証

数値、確率、式を含む案は、Prototype実装または有力案として進める前に、必要に応じて次を確認する。

- 期待値、分散、境界条件、極端ケース
- 長期シミュレーション、支配的戦略、入力感度

目的はAIに最適値を決めさせることではなく、Prototypeで検証する価値があるかを判断する材料を増やすことである。初期アイデアや、まだ数式化する段階ではない未決事項に、この工程を必須化しない。

## 6. 敵対的プレイテスト

単純な戦略を持つBotによるプレイテストは、将来の導入候補とする。目的は最適解の探索ではなく、極端に単純な方針が他の選択肢を支配していないかを検出することである。

候補となる方針には、常に最大スタミナ投入、最小単位投入、毎回宿屋へ戻る、Goldをすべて強化へ使う、特定ロケーションだけを周回する、戦術を固定する、毎戦戦術を変更する、などがある。

比較候補には、第1層クリアまでの探索処理数、スタミナ投入量、戦闘数、敗北数、Gold、EXP / Lv、装備・強化状態、HP / MP / 満腹度の推移などを用いる。

これはHuman Verification前の反証材料であり、単独でゲーム仕様の変更や面白さの判定を決めるものではない。現在、この仕組み自体は実装しない。

## 7. バランス探索

AIへ自由に「ちょうどよい値」を決めさせない。先に人間が、想定勝率、平均戦闘ターン、平均被ダメージ、必要Gold、必要EXP、探索回数などの許容帯を定める。

AIやシミュレーションは、複数条件を同時に満たすパラメータ候補の探索に使う。最終数値と意図的な例外は人間が決定する。

## 8. Human Verification支援

HV自体は人間が行う。

### HV前

- 確認項目、検証仮説、検証用fixtureを整理する
- 仮説が誤っていた場合に観測される結果を整理する

### HV後

- 観測事実と人間の感想を分けて記録する
- 想定原因、別原因候補、今回の変更と無関係な可能性を整理する
- 次に切り分ける仮説候補を整理する

原因の確定、次Issueの選択、仕様への昇格は人間が行う。

## 9. テスト・QA

データから機械的に導ける不変条件は、データ駆動で検証する方向とする。対象例は、確率合計、重複ID、ID参照整合、必須フィールド、数値範囲、CONFIG参照、save → load、migrationの冪等性である。

目標は、コンテンツ数が増えてもテスト記述量を同じ割合では増やさないことである。対象変更に応じた通常のPrototype検証入口とsimulationの選択は、`AGENTS.md`の検証ルーティングに従う。

## 10. コンテンツ制作

敵、素材、武器、防具、アイテム、レシピ、探索イベント、ロケーションなどは、次の流れを候補とする。

```text
人間が必要な役割を定義
→ 型・制約
→ AI候補生成
→ 自動検証
→ 問題候補を警告・除外
→ 指標付き候補
→ 人間選定
```

最大化するのは生成量ではなく、1回の人間判断で処理できる候補の質と量である。候補生成を正式仕様の自動決定や、人間選定の代替として扱わない。

## 11. 第2層の位置づけ

100層全体の制作方式は現時点で正式決定しない。第2層は、必要になった段階でコンテンツ制作方式そのものを検証するPrototypeとして利用することを検討する。

比較候補は、人間による個別設計、アーキタイプ、層係数などによるパラメータ化である。検証する問いは、型化・パラメータ化しても第2層が第1層の単純な使い回しに感じられないか、である。

これはPrototype検証テーマであり、正式な100層制作方式ではない。

## 12. 導入Phase

### Phase 1：既存開発基盤の補強

既存の`DOC_MAP.md`、`AGENTS.md`、Issue / PR Template、検証スクリプトを作り直さず、PR影響範囲、関連SSOT、Decision再検討、Test / Simulation / HV / Docs Sync状態などの不足を小さく補う。最初から集計システムや万能監督AIは作らない。

### Phase 2：敵対的プレイテストの最小実験

第1層を対象に、単純戦略の比較が反証材料として有効かを確認する。

### Phase 3：1種類のコンテンツ生成パイプライン

通常敵など1種類だけを対象に、候補生成から人間選定までの流れを試す。

### Phase 4：第2層で制作方式を比較

一部のコンテンツで、手作り、アーキタイプ、パラメータ生成を混在させ、制作方式そのものを検証する。

### Phase 5：有効性が確認できた仕組みだけ展開

結果を確認できた仕組みだけを、他カテゴリへ展開する。

この文書の追加時点では、Phase 1の具体的な実装Issue作成と、Phase 2以降の実装は行わない。

## 13. 新しいAI活用案の判断基準

新しい案は、次の順で判断する。

1. 本当に人間が行う必要があるか
2. 受入条件を機械的に判定できるか
3. AIにより人間の判断材料が良くなるか
4. AI導入によってレビュー量が増えないか
5. 今必要か
6. 小さなPrototypeで検証できるか

将来必要になるという理由だけで、汎用基盤化しない。

## 14. 現在の実装との関係

最新`main`（この文書の確認時点では`739e1cf4de4158bb3f65bbd1a97bb81e3d332d1c`）には、次の基盤が存在する。

- `docs/DOC_MAP.md`を入口としたSSOTルーティング
- `AGENTS.md`によるAgent共通ルール
- Issue単位のScope / Out of Scope / Acceptance Criteria
- PR上の設計書影響確認
- Agent VerificationとHuman Verificationの分離
- Prototype変更に対する`python3 scripts/check_prototype.py`のfull regression入口
- 変更領域別のsimulationルーティング
- HV未完了時に`REVIEW_REQUIRED`として人間へ引き渡すルール

一方、敵対的プレイテスト、コンテンツ生成パイプライン、PR状態の自動集計、検証状態の統一形式、万能監督AIは、現時点の標準運用として実装済みとは扱わない。

ゲーム仕様・Prototype仕様・確定度はこの文書で変更しない。個別Issue固有の検証方法、具体的な数値、単発スクリプトの使い方も原則として追加しない。

## 15. 文書更新条件

次の場合、この文書の更新候補とする。

- AIと人間の責務分担を変更する場合
- 標準的な検証順序を変更する場合
- 新しい検証レイヤーを恒常運用化する場合
- コンテンツ制作方式の方針レベルを変更する場合
- 第2層などで検証した方式を標準運用へ昇格する場合

更新時も、この文書をゲーム仕様のSSOTへ昇格させない。ゲーム仕様に影響する判断は、`docs/DOC_MAP.md`で関連SSOTを特定し、必要な設計文書とIssue / Decisionを別途更新する。
